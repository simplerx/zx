# Zx 设计裁定记录

> 状态：**v0.5 已定稿**。本文只记"为什么这么定"，语法细节看 `zx-spec.md`，语法形式看 `zx.ebnf`。
> 每条形如：**问题 → 裁定 → 代价**。代价一律写清楚，方便以后反悔时知道要改多少东西。

---

## 1. 取地址用 `&`，`*T` 只做指针类型

**问题**：`plan` 原文写 `*` 既当指针类型又当取地址（`var px = *x`），和 C 系的阅读习惯冲突，且 `*x * *y` 无法解析。

**裁定**：

```
&x       取地址      →  *T
*T       指针类型
p.0      解引用（第 0 个元素）
p.f      ≡ p.0.f    自动穿透一层
```

没有独立的解引用运算符，也没有 `->`。解引用统一走 `.0`，因为数组访问和指针解引用在语义上本来就是同一件事（指针就是一个长度未知的数组）。

**代价**：`.0` 同时承担"数组下标 0"和"解引用"，读 `p.0.0` 时要想一下。换来的是**全局只有一种指针语法**。

---

## 2. 数组就是指针，但数量在类型里：`*[N]T`

**问题**：`plan` 说"数组就是一个指针，但编译期可知长度"。这两句放在一起，长度到底在哪？

**第一版裁定（v0.2）**：长度只是注解，`*[N]T ≡ *T`。
**最终裁定（v0.3）**：**长度进类型**，`*[N]T` 和 `*[M]T` 是不同类型；`*T` 单独作为"数量未知的裸指针"。

```zx
*[3]i32     数组，8 字节，N=3 在类型里
*[4]i32     另一个类型
*i32        裸指针，数量未知，又是另一个类型
```

三者表示相同（一个地址），`@sizeOf` 都是 8，传参都不复制——"数组就是指针"说的是**表示**。而 N 进类型带来的是：

- `.len` / `.size` 有确定来源（就是 N），不再依赖"声明处记不记得"
- 函数签名能表达"我只要 3 个"：`fn dot(a: *const [3]f32, b: *const [3]f32) f32`
- 泛型参数 `n` 直接进类型，不同 `n` 自动单态化成不同代码
- 误传长度不同的数组，编译期就报错，不用等到运行时越界

**为什么第一版错了**：把 `[N]` 降级成注解后，`.len` 变成了"看上下文"的东西——同一个 `*i32` 变量，赋值路径不同 `.len` 可能失效，语义分析里必须额外维护一份"长度证据"的旁路信息。而这份信息本来就在类型里。

**代价**：
- `*[3]i32` 不能直接赋给 `*[4]i32`，要显式 `(*[4]i32)p`（这是特性，不是缺陷）
- `*T` → `*[N]T` 必须显式转换（"我保证有 N 个"，编译器验证不了）
- 结构体里仍然不能内联数组，只能内联指针（"数组即指针"的必然结果，接受）

## 3. 数组字面量是 `&.{…}`，元组字面量是 `{…}`

**问题**：两个都要用花括号，怎么分？

**裁定**：**差一个点**。

```zx
{1, 2, 3}      元组 —— 值类型，内联，元素类型可以不同
&.{1, 2, 3}    数组 —— & 取地址 + .{ 是字面量标记，结果 *T
```

这个 `.` 不是随手加的，它解决一个真问题：`&` 后面是**前缀操作数位置**，那里的 `{` 既可能是块也可能是字面量。

```zx
&{ let a = 1; break a; }   // 取一个块的值的地址？
&{1, 2}                    // 还是取一个元组的地址？
```

写成 `&.{` 后，词法层就确定了。所以 `.{…}` 是"强制字面量"标记，任何地方都能用（`.{1,2}` ≡ `{1,2}`），而 `&.{…}` 是它的固定搭配。

**`{…}` 的消歧规则**（parser 用，可判定）：

> 从 `{` 扫到匹配的 `}`，只看顶层（跳过嵌套）：出现 `;` 或 `const`/`let`/`var`/`fn` → 块；否则 → 元组。

强制块的位置（函数体、`if`/`while`/`for` 的体、类型体、switch 体）不受影响，那里的 `{` 永远是块。

**代价**：`if` 的块臂不产生值（见 §13），要交出元组就写表达式臂：`if (c) => {1, 2} else => {3, 4}`。换成"`if` 体可以是任意表达式"会引入悬垂 `else`，不值得。

## 4. `.len` / `.size` 是编译器字段，不占内存

**裁定**：

| 字段 | 含义 |
|---|---|
| `.len` | 元素个数 |
| `.size` | 字节数（`len × @sizeOf(T)`） |
| `.ptr` | 仅切片：`s.ptr` 是 `*T`（数组丢数量直接隐式转换，不需要 `.ptr`） |

长度已知时（`*[N]T`、`&.{…}`、元组）**两者都是编译期常量，运行时没有任何读取动作**。切片 `[]T` 的 `.len` 是运行时值（切片真的存了它）。

**代价**：`len` / `size` / `ptr` 三个名字不能再当结构体字段名，声明时直接报错。这是"用 `.` 统一访问一切"的必然代价，比 Zig 的 `@field` 一族便宜得多。

**未知长度的指针**：`*i32` 上读 `.len` 是编译错误，报错文案直接指路 `[]T` 或 `@sizeOf`。

## 5. `let`：补上"运行时不可变"

**问题**：`plan` 要求"凡是 `const` 必须编译期可知"。严格执行的结果是**语言里没有只读局部量**：

```zx
var x: i32 = 1;
var p: *i32 = &x;      // 想表达"这指针我不改"，但 const 写不了
var n: i32 = p.0;      // 每个临时量都成了 var
```

函数里几乎每行都是 `var`，看代码分不清"可变状态"和"刚算出来的临时量"。

**裁定**：三档绑定。

| 形式 | 求值 | 存储 | 可写 | `&` 得到 |
|---|---|---|---|---|
| `const X = e;` | **必须编译期** | 无（折叠 / 静态数据） | 否 | `*const T` |
| `let X = e;` | 运行时 | 栈 / 字段 | 初始化后否 | `*const T` |
| `var X = e;` | 运行时 | 栈 / 字段 / 静态 | 是 | `*T` |

`const` 的语义**一个字没改**（还是编译期），只是"不可变"被拆成两种实现。不违背"只分可变和不可变"这条原则。

**代价**：关键字多一个；语义分析里 `const` 是"值"、`let` 是"槽位"，不能混。

## 6. 参数与捕获：只读运行时槽位

**问题**：`const` 要求编译期，函数却要收运行时参数。

**裁定**：参数和 `if`/`while`/`switch` 的捕获名是**只读槽位**，不写修饰符：

- 只读，函数体内不可赋值（要可写写 `var a: T`，该参数强制运行时）
- 是 comptime 还是 runtime，**由调用点决定**：实参全编译期 → 整次调用编译期完成
- 捕获是值拷贝；`&v` 得到指向槽位的 `*const T`

这是让"`const` 必编译期"和"函数收运行时参数"共存的最小代价，也是 Zig 的 comptime 语义。

## 7. 联合体：Zig 形态 + 少写一对竖线

**裁定**：声明沿用 `plan` 的 `成员: {标签, 载荷类型}`，其余全按 Zig：

```zx
const Shape = union {
    circle: {ShapeTag.circle, f64},
    rect:   {ShapeTag.rect,   {f64, f64}},
};

let s = Shape{ .circle = 2.0 };          // 标签由编译器填，不用手写
let area = switch (s) {
    .circle => |r| 3.14159 * r * r,      // switch 上要求穷尽
    .rect   => |t| t.0 * t.1,
};
```

**唯一偏离 Zig 的地方**：`if` 捕获 `?T` / `!T` 时省略竖线。

```zx
if (maybe) v { use(v); }                 // Zx：直接写捕获名
if (maybe) |v| { use(v); }               // Zig
```

理由：`if` 捕获在 `?T`/`!T` 上出现频率远高于 `switch`，省两个字符收益明显，而且 `if (u) v {` 读起来就是"如果 u 有值，就叫它 v"。`switch` 保留 `|x|`，因为那里有歧义风险（`case => expr` 后面紧跟标识符会被误读）。

**代价**：两套捕获语法。接受——它们长得像，语义一致，不会真的记混。

## 8. 编译期 = 一个解释器

**裁定**：`type` 是一等编译期值，泛型就是编译期函数，模块是编译期内置函数。三者共用同一个求值器。

```zx
const List = fn (T: type) type { return struct { data: []T, len: usize, cap: usize }; };
const Buffer = fn (T: type, n: usize) type { return struct { data: *[n]T, len: usize }; };
```

实现顺序上 **M2（编译期解释器）是分水岭**：写对了，泛型、类型即值、const 函数全部白送。所以先写它，别先写代码生成。

`const` 语境下算出来的指针和聚合值会**物化为静态数据**，所以允许"指向编译期局部量的指针"逃逸出块（`POW2` 那张表就是这么来的）。

## 9. 存储从哪来（`&.{…}` 与 `undefined`）

**问题**：`var a: *[16]i32 = undefined;` 到底是"16 个 i32"还是"一个地址"？

**裁定**：类型上永远是 8 字节指针；**是这条声明额外申请了存储**。

| 写法 | 存储 | 可写 |
|---|---|---|
| `var a = &.{…};` | 当前栈帧 | 是 |
| `let a = &.{…};` | 当前栈帧，之后只读 | 否 |
| `const a = &.{…};` | 静态数据 | 否 |
| `var buf: *[N]T = undefined;` | 当前栈帧，N×sizeof(T) | 是 |

`undefined` 是"只要空间不要值"的唯一入口。其他初始化器一律只是指针值。

**代价**：`*[N]T` 在两种写法下含义不同（类型 vs 申请空间），这是本设计里最需要看文档的一处。但它语法可判定，实现成本很低。

## 10. `for` 只吃两种序列，但可以同时吃好几个

**裁定**：`for` 的序列只能是

```
[]T        切片
lo..hi     整数范围（左闭右开，两端同型整数）
lo..       省略上界的范围 —— 只在多绑定时合法，上界取其他序列的公共长度
```

绑定名**直接写，不带竖线**；**序列个数 = 绑定个数**：

```zx
for (xs) x { … }                 // 单绑定
for (xs, 0..) x, i { … }         // 值 + 下标
for (xs, ys) a, b { … }          // 两个等长序列
for (0..n) i { … }               // 纯整数范围
```

数组 `*[N]T` 和元组都不是序列，要先变切片：

```zx
for (xs[0..]) x { … }            // *const [5]i32 → []const i32，零开销
```

**为什么支持 `0..` 这个省略上界的写法**：没有它，"带下标遍历"只能写 `for (0..xs.len) i { xs[i] }`，多一次乘法和一次边界检查，而且长度得手写一遍。而 `0..` 的长度由同一次 `for` 里别的序列给出，语义上不是"无限范围"，只是"和旁边那个一样长"。单序列时 `for (0..) i` 没有长度可借，报错。

**等长检查**：长度编译期已知（`*[N]T`、字面量）→ 编译期报错；否则安全模式下运行时断言。默认不做"取最短"，因为长度不一致几乎总是 bug。

**为什么不支持枚举/元组**：每多一种可迭代对象，`for` 就要多一套语义（枚举的顺序是什么？元组元素类型不同怎么统一？）。要的都能用范围写：

```zx
for (0..3) i { … }               // 枚举：变体值就是 0,1,2
```

**代价**：`for (xs[0..])` 多打 4 个字符。换来的是 `for` 的语义只有一条规则。

## 11. `defer`：离开作用域时执行

**问题**：没有 GC、没有 RAII、没有析构，手工配对 `lock/unlock`、`alloc/free` 一定漏。

**裁定**：

```zx
defer expr;
defer { … }
```

- 在**所在块退出时**执行一次：正常结束、`break`、`continue`、`return` 都算
- 同一块内多个 `defer` **逆序执行**（LIFO）
- 表达式**在退出时求值**，不是 `defer` 那一行求值
- 是语句，不产生值，不影响块的值
- `defer` 体内禁止 `break` / `continue` / `return`

**注意陷阱**：`return` 的值先算出来，`defer` 才跑。所以

```zx
defer alloc.free(buf);
buf                      // 返回值指向已释放内存
```

是错的。`defer` 只适合"清理不影响返回值"的场景。要"成功不清理、失败清理"，需要 `errdefer`（v0.2 候选，不是现在）。

**为什么不用 RAII/析构**：析构要求每个类型都有隐藏的销毁逻辑，和"作用域就是一个值"直接冲突（一个值是元组还是结构体，销毁顺序都要规定）。`defer` 显式写在代码里，读代码就能看见副作用发生在哪。这与"简洁"的目标一致。

## 12. 后端先出 C

**裁定**：M4a 生成 C，M4b 再考虑 LLVM。

**理由**：
- 最快跑通端到端。C 编译器免费提供寄存器分配、指令选择、链接，你只需要关心"语义对不对"。
- `?T`/`!T`/带标签联合体的布局本来就是普通 struct + tag 字段，映射到 C 毫无损失。
- 出 C 之后，用 `gcc -O2` 就能有一份可用的性能基线；将来切 LLVM 时这份基线就是对照。

**代价**：
- C 没有 `noreturn` 之外的控制流保证，`defer` 要手工展开成 goto 链（可接受，Zig 早期也这么干）
- 编译期求值的浮点和 C 的浮点可能差 1 ULP（可接受，先不追）
- 出 C 会限制一些优化（比如 `?T` 的 niche 优化），但那是 M5 之后的事

## 13. `{x}` 是元组，所以块的值不能来自末尾表达式

**问题**：块和元组共用 `{…}`。原方案是"块的值 = 末尾表达式"，于是 `{x}` 是个有值 x 的块。但元组也需要 `{x}` 表示一元组——**同一个写法不能有两个值**，只能留一条规则。

**裁定**：`{x}` 是一元组。无标签块的值恒为 `{}`。判定块还是元组只看顶层有没有 `;` 或声明：

```zx
{ x }          // 一元组 {T}
{ x; }         // 块，值 {}（x 是表达式语句）
{ x = 0; }     // 块，值 {}
{}             // 空元组 = void
```

**为什么留这条**：它让花括号的身份**完全由语法决定**。原方案要在语义分析里维护"这个 `{` 到底是块还是元组"的猜测，而且 `{ f() }`（一个调用）永远处于灰色地带；现在只看有没有 `;`，parser 一次前向扫描就定死。

**连锁 1：函数体不再有末尾返回值。**

```zx
const f = fn () i32 { 1 };            // ✗ 块值 {} 不是 i32
const f = fn () i32 { return 1; };    // ✓
```

**连锁 2：`if` 的块臂不再有值——值靠标签收割（§18）。**

```zx
let max = if (a > b) a else b;        // 表达式臂（糖）
let sign = s: if (x > 0) { s: 1; } else { s: 0; };   // 标签加在 if 上
```

**连锁 3：提前离开嵌套结构靠标签收割，且收割会穿过无标签结构。** 在循环里写收割语句，命中的是外面（或循环自己）的标签作用域，不会"只结束一个分支"——§13 原来担心的"break 落错目标"的坑，在收割模型里天然不存在，因为**收割必须写标签名**，目标永远显式。

**代价**：
- 所有"最后一个表达式当返回值"的写法都要加 `return` 或收割。这是真实的可读性成本。
- `fn f() i32 { 1 }` 这种顺手写的代码会报错，需要一次适应。

**换来的**：`{x}` 永远是元组；块值规则只有一句；控制流目标永远显式（带标签名）。

## 14. `?T` / `!T` 的布局：载荷在前，标签在后

**问题**：`?T` 是 `{tag, payload}` 还是 `{payload, tag}`？

**裁定**：**载荷在前**。

```
?T   { payload: T @0,  tag: bool  @sizeof(T) }
!T   { payload: T @0,  tag: error @sizeof(T) }

align(?T) = align(T)
sizeof(?T) = align_up(sizeof(T) + 1, align(T))
```

**修正（v0.6，写 C 后端时发现）**：`!T` 的 tag 是 2 字节的 `error`，
若照 `align(!T) = align(T)` 直算，`sizeof(!u8) = align_up(1+2, 1) = 3`，
tag 就落在偏移 1 —— **u16 未对齐**，在 ARM 上直接 fault。所以对齐要抬高：

```
align(!T) = max(align(T), 2)
sizeof(!T) = align_up(sizeof(T) + 2, align(!T))
```

代价只有一个：`sizeof(!u8)` 是 4 而不是 3。零尺寸 payload 时也只是多两个填充字节。
载荷仍在偏移 0，§14 的核心性质（`&x` 就是 `&payload`）不受影响。

**理由**：`&x`（`x: ?T`）拿到的是 payload 的地址，所以

```zx
const p: *const i32 = &x;        // x: ?i32，零偏移，和 &x.payload 同一地址
```

是**零转换重解释**，不需要知道 `align(T)`。反过来若标签在前，payload 的偏移是 `align_up(sizeof(tag), align(T))`，`@ptrCast` 到 `*T` 会静默错位——这类错误不会崩，只会读错数据，是最难查的一类。

**代价**：
- 标签的偏移不是常量 0 而是 `sizeof(T)`，读标签多一个加法（常量折叠后就是固定偏移，无成本）。
- 和 Zig 的 `?T` 布局不同（Zig 是 tag 在前），ABI 不互通。反正 Zx 的 ABI 只对自己负责。
- 当 `T` 是零尺寸类型（`void`、空结构体）时 payload 占 0 字节，tag 在偏移 0——这是唯一退化的情形，无害。

## 15. 格式化：能编译期就编译期

**裁定**：`std.print` / `std.println` / `std.format` 走两条路径，语义完全一致：

1. **`fmt` 是编译期常量**（字符串字面量、`const` 串、它们的拼接）→ 编译期解析成"逐段输出"的直接调用序列，运行时零解析、零分配。
2. **`fmt` 是运行时值** → 回落到运行时解析器，慢，但行为一样。

**为什么两边都要**：只做编译期，日志/国际化这种"格式串来自变量"的场景直接不可用；只做运行时，90% 的情况白付解析成本。而"能编译期就算"恰好是 Zx 已有的能力（`const` 就是编译期值），不需要新机制。

**实现**：编译期路径把

```zx
std.print("x = {}, y = {}\n", x, y);
```

展开成

```c
fwrite("x = ", 1, 4, stdout); zx_print_i32(x);
fwrite(", y = ", 1, 6, stdout); zx_print_i32(y);
fputc('\n', stdout);
```

运行时路径就是同一棵"格式片段树"的解释执行——同一份解析器，编译期跑在 `const` 值上，运行时跑在 `[]const u8` 上。所以两条路径不会出现行为差异，测试一套就够。

**代价**：编译期路径下，格式串里的错误（占位符数量对不上、类型不可格式化）是编译错误；运行时路径下是运行时报错——**同一个 bug，两种报错时机**。这是无法消除的，因为运行时才知道格式串长什么样。

## 16. 删除 `break`：标签收割（v0.5）

**问题**：v0.4 里 `break :tag v` 把"跳出"和"带出值"拆成了关键字 + 标签两件事；同时 `if` 需要专门的 `=>` 臂才能有值。三个机制（`break`、标签、`=>`）表达的是同一件事：**离开作用域并交出值**。

**裁定**：合并成一条语句——**收割** `tag: expr;`。给最近一层名为 `tag` 的标签作用域设值，并立即离开它。`break` 和 `=>` 从语言里删除。

```zx
// 一次跳出两层，值是下标元组（原 break :outer {i, j}）
outer: for (0..rows) i {
    for (0..cols) j {
        if (grid[i][j] == 0) { outer: {i, j}; }
    }
} else null;

// 块算值 + 中途退出（原 break :shape）
let area = shape: {
    if (w <= 0) { shape: 0; }
    shape: w * h;
};

// if 表达式臂就是糖：if (c) 10 else 0
let max = if (a > b) a else b;
```

**为什么收割比 `break` 好**：

1. **目标显式**。`break` 不带标签时跳"最近的目标"，读代码要往外数花括号才知道跳到哪；收割必须写标签名，目标写在语句里。
2. **一条规则覆盖所有场景**。跳出循环、块交值、if 分支给值、switch 块臂给值——全是"标签作用域 + 收割"，不再需要 `break` / `=>` 两套机制。
3. **关键字更少**。控制流关键字只剩 `continue` 和 `return`。
4. **与"只有带标签的块才返回值"自洽**。无标签块既不能交值也不能被提前离开——块的"有没有值"由有没有标签决定，完全语法可判。

**代价**：

1. 无标签循环不能提前退出，必须加标签。写惯了 `break` 的人要多打 5 个字符（`tag: ` + 改写）。**这是一处需要适应的显著变化**——但换来的是每个控制流出口都有名字。
2. `tag: {i, j};` 里 `{i, j}` 要套用花括号消歧判定是元组还是块（元组 → 收割，块 → 标签作用域）。判定规则和 §4.1 是同一条，没有新增复杂度，但读者要知道这条联动。
3. 收割语句和标签作用域共用 `IDENT ":"` 前缀，靠后面的 token 区分（`for`/`while`/`switch`/`if`/块 → 打标签；其他 → 收割）。parser 一次前看即可。

**换来的**：控制流模型从三条规则（break / 标签 / `=>`）变成一条。

**连带裁定**：

- **`switch` 去掉 `|x|` 载荷捕获**。臂改用 `模式: 体`，联合体载荷用 `s.成员` 访问。理由：`if` 捕获已省略竖线，`switch` 再保留 `|x|` 是两套风格；`switch (s.tag)` + `s.circle` 的写法和 `?T` 的裸接口一致。
- **循环 `else` 支持值形式** `else 表达式`：正常跑完时循环的值。原来 `else { break 0; }` 的写法随 `break` 一起消失。

## 18. `pub`：可见性写在声明这一头（v0.6）

原来的规则是"`_` 前缀 = 私有，其余导出"。这条路子有两个毛病：

1. **默认是公开的**。加一个内部辅助函数得先知道"得给它加下划线"，忘了就是 API。
2. **`_` 已经是丢弃占位符**（`const _ = f();`），一个符号身兼两职迟早出事。

所以反过来：**默认私有，想导出写 `pub`**。

```zx
pub const add = fn (a: i32, b: i32) i32 { return a + b; };
const helper = fn () i32 { return 1; };        // 私有
```

- 只允许出现在文件作用域；写在函数体里是错误（不是警告——它没有任何意义）。
- `pub` 只影响"别的模块能不能看见"，不影响本文件：本文件里公私有完全一样。
- 没有 `pub struct` 这种写法：类型是 `pub const Point = struct {…}` 的值，
  `pub` 加在 `const` 上就够了。
- 错误信息带模块名：`'secret' is private to module 'util'; mark it \`pub\` to export it`。

## 19. 编译期视图：V_PTR 就是"底层 + 偏移 + 长度"

R1 要求 `const` 必须算得出来，于是 `const head = str[0..2]`、`const m0 = mid.0` 这类
写法也必须能折。做法是**不复制数据**：

```
V_PTR { base = 底层 V_AGG（或 V_STR）, off = 元素下标, nitems = 可见长度 }
```

- `s[lo..hi]` → 新 `V_PTR{ base, off + lo, hi - lo }`（字符串则直接产生一小段 `V_STR`）；
- `p.0` / `p[i]` → `base[off + i]`，越界在编译期报错；
- `.len` → 切片看 `nitems`，`*[N]T` 看类型里的 N；`.size` 用 `ty_size_relaxed`
  （comptime_int / comptime_float 按 R7 的默认宽度算）；
- `&x` → `V_PTR{ base = x 的编译期值 }`，指向视图就等于视图自身。

**后端例外**：视图型全局不物化成静态数据。物化会把数据复制一份，之后往原对象里写
就看不见了（`var arr = &.{…}; const view = arr[0..]; arr.1 = 99;`）。所以这类初值
放到 `zx_init_globals()` 里按源码表达式求值——值仍然是编译期算出来的，
只是地址的落地推迟了一点点。

## 20. 读 `var` 只在编译期执行时才算数

`const k = n + 1` 里的 `n` 是 `var` 时会怎样？编译器当然知道 `n` 现在等于 3——
但下一行可能就改成 5。

规则：**`var` / 参数 / 捕获的读取只在编译期真的"在跑"的时候有效**（被折叠的块/循环/
编译期函数体里，`g_ct_exec > 0`），普通表达式里读到它们就是"没有编译期值"，
于是 R1 直接报错。这样 `const` 的语义不会被"恰好现在是这样"绑架。

顺带一条实现经验：编译期递归函数（`fib`）在**检查体**的时候不能折叠对自身的调用，
否则 `if (n < 2) return n;` 的另一支会一路 `fib(-1) → fib(-2) → …` 打穿栈。
所以检查阶段（`g_ct_checking`）遇到栈上的函数就让给运行时，执行阶段不受限。

## 21. 缺返回路径：这是到达性问题，不是类型问题

`fn f(n: i32) i32 { if (n > 0) { return 1; } }` —— 类型看没问题（`return 1` 确实是
`i32`），但条件不成立时函数掉出末尾，返回的是一个**不存在**的值。C 里这是 UB，
所以必须在编译期拦住。

关键认识：这不能靠"最后一条语句是不是 return"来判，要做**到达性分析**。能拦住
路径的只有三样：

1. `return` / `continue`；
2. 类型是 `noreturn` 的表达式（`@trap()`、noreturn 函数调用）；
3. 退不出来的循环 —— 只有 `while (true)`。`for` 的序列一定有限（`lo..` 由别的
   序列定长度，见 §8.3），所以 `for` 总会结束，不能算拦住了路径。

`if` / `switch` 要**每条出路**都拦住才算拦住。`switch` 还要求覆盖穷尽：

| 类型 | 穷尽的判据 |
|---|---|
| 枚举 / 带标签联合体 | 每个变体都有臂 |
| `?T` | `.some` + `.none` |
| `!T` | `.ok` + `.err` |
| bool | `true` + `false` |
| 整数 | 从不认为穷尽（按值匹配，不要求列全） |

没有独立的"switch 穷尽性检查"：漏一个变体的后果**就是**一条掉出函数的路径，
所以这个判据只在缺返回分析里用。写 `else` 就等于自己声明"剩下的都归它"。

两个例外，写下来是为了以后别再纠结：

- **`main` 掉出末尾 = `return 0`**。后端本来就发 `return 0;`，要求手写只是仪式感。
  但 `fn main() noreturn` 仍然必须真的回不来。
- **`noreturn` 函数也不许掉出末尾**：声明"我不返回"，结果能掉出去，那是撒谎，
  也是 UB。

同一份源码可能被单态化出很多份身体（泛型），错误只在源码位置上报一次。

顺带修掉的两个真 bug（都是这条分析逼出来的）：

- `for (0..)` 曾经生成 `_i0 < 0`（当成"长度 0"），循环一次都不跑，`spin()` 直接
  返回 0。`lo..` 单独出现现在按 spec §8.3 报错，后端也不再把它当零长度。
- `@trap()` 在检查阶段折叠时报过 "reached at compile time"。它只在编译期真的
  执行到时才算"到达"，普通表达式里就是运行时操作。

## 22. 不可达代码：缺返回分析的同一条判定，换个方向用

缺返回分析问的是"块末尾到得了吗"，不可达代码问的是"这条语句之后还到得了吗"。
两者共用一份判定：`stmt_blocks_next()` 就是在 `stmt_ends()` 上多认一个"收割"
（`tag: expr;` 会跳出所在块），其余原样复用。

一个刻意保留的保守：**标签块不能判成"后面到不了"**。`out: { … }` 收完值就接着
往下走，而 `falls_through` 不认收割，所以 `stmt_ends(块)` 只在块里真的
`return` / `continue` 时为真——刚好正确。

只报一次，按 (line, col) 去重。原因是编译期折叠会把函数体 clone 一份再检查
（`ct_call` → `clone_tree`），同一句会走两遍；按位置去重比按指针可靠。

报错时会点出"是哪一句把路堵死的"：

```
unreachable code: the `return` above never falls through
unreachable code: the `while (true)` above never falls through
unreachable code: the `switch` above never falls through
```

这是**错误**不是警告：能判定的死代码没有保留的理由，留着只会在改代码时误导人。

## 23. 运行时格式化：同一套语法，两条实现

`std.print` / `println` / `format` 的格式串有两种来源，两条路径共用同一套语法：

| fmt | 路径 | 代价 |
|---|---|---|
| 编译期常量 | 拆成 printf 串，零解析 | 无 |
| 运行时值 | `zx_fmt` 现场解析一遍 | 每次一行循环 |
| `std.format` 的任何 fmt | 总是运行时缓冲（量长 → 分配 → 再写） | 两遍解析 |

几个具体决定：

- **实参统一成 `ZxFmtArg`**（`kind` + `long long` + `double` + `ptr/len`）。
  每个实参只求值一次，靠 `zx_fa_i/u/f/b/s/c/p` 这些小函数——如果直接展开成
  `{ … expr …, … expr … }`，切片参数会被求值两次（编译期路径就有这个老毛病）。
- **类型规则必须与编译期路径逐条对齐**，所以分派顺序也照抄 `fmt_spec`：
  字符串 → `{c}` → bool → 浮点 → `{b}` → 整数 → 指针。`{d}` 套在字符串上
  仍然打印字符串，不报错——两条路径行为一致比"更严格"重要。
- **判不了就运行时报**：编译期能数的（占位符个数、`{N}` 越界）在 sema 里报；
  fmt 是变量时只能运行时，`zx: format error: …` 之后 `abort()`。
- **`std.format` 的分配器是普通值**，不是编译器魔法：

  ```zx
  const Allocator = struct {
      alloc: fn(usize) ?*u8,
      free:  fn(*u8, usize) void,
  };
  ```

  类型身份靠一个合成节点（`sema_allocator_type()` 里的 `static Node id`），
  唯一用途是让后端给它的 C 结构体一个稳定编号。`std.heap.page` 是个
  `SK_CONST` 符号，C 名固定为 `zx_alloc_page`，值就是 `{zx_page_alloc, zx_page_free}`。
  自定义分配器这条路已经通了（结构体字面量 + 字段调用），但目前做不出真的
  arena：指针算术 `p + n` 和 `(usize)p` / `(*u8)i` 的代码生成还没写。

- `std.format` 结果末尾补 `\0`，所以 `s.ptr` 可以直接当 C 串；释放用
  `alloc.free(s.ptr, s.len)`。
- 两遍解析（量长度 + 写）是刻意的：一遍要多一个可增长的缓冲区，而这里
  只有一次分配、没有失败回滚的麻烦。

## 24. 指针算术按元素算，C 那边要先把类型退成元素指针

`p + n` 挪 **n 个元素**，`p - q` 得 **元素个数**（`usize`）。这和 C 的指针加法一致，
但我们的 `*[N]T` 在 C 里是 `T(*)[N]`——直接 `+1` 会跳 N 个元素，正好差一个数量级。
所以后端生成的是：

```c
/* (p: *[4]i32) + n  */
((int32_t *)((int32_t *)(p) + (n)))
```

`p - q` 同理，两边都先转成元素指针再减，结果 `(size_t)`。

几条边界，都是为了让"一个类型一个说法"：

- **结果类型永远退化成 `*T`**：`arr + 1` 是 `*T`。数量没法跟着减，与其发明
  `*[N-k]T`，不如老老实实丢掉——这也和 R7.1（`*[N]T → *T`）是同一个方向。
- **偏移量只收 `usize`**（字面量例外，直接定型成 `usize`）。`i32` 偏移报错并且
  在信息里写出解法 `(usize)…`——R4 说没有隐式数值转换，指针算术不是例外。
- **`p - q` 要求两边元素类型相同**；`p + q` / `p * n` / `p < q` 都是错误。
- 指针算术的结果**仍然是视图**（`is_view_expr` 认了 `NK_BIN`）：全局的
  `const mid = arr[0..].ptr + 1;` 不能物化成静态数据，否则又成了"另拷一份"。

编译期也折叠：`V_PTR` 上的 `±` 只挪 `off`，`p - q` 要求同一个 `base`
（不是同一个底层对象就没有"差几个元素"这回事）。

顺带修的两个真 bug：

- **`?T` 的 tag 语义反了**。运行时辅助函数（`zx_page_alloc` / `zx_format`）把
  `tag` 当"失败标志"用，而语言里 `?T` 的 tag 是"**有值**"（`!T` 的 tag 才是错误码，
  且 0 表示 ok）。内置分配器自己两头都是反的所以自洽，用户写的分配器一接上就
  永远拿到"分配失败"。现在统一成语言语义。
- 指针的 `catch`/赋值到 `?*T` 那条路径上，`ensure_type` 不会去注册被指向的结构体，
  于是 `?*Node` 的 typedef 里先出现了还没声明的 `ZxS1`。

## 25. 自引用类型：先挂外壳，再填成员

R5 说"自引用类型天然合法"，但 `const Node = struct { next: *Node }` 一开始是
`cyclic dependency while resolving 'Node'`——因为解析 `Node` 的过程中又要求解析 `Node`。

做法是给符号加一个中间状态（`state == 3`，含义是"外壳已就绪、成员表还没填"）：

1. 解析 `const X = struct/union {…}` 的初始值**之前**，先用 `ty_agg(kind, decl, NULL)`
   建出那个（interned 的）聚合类型，挂到 `s->type_val`，状态置 3；
2. `resolve_type` 遇到 `state == 3` 的符号，直接还它外壳，不走 `ensure`；
3. 真正的成员表随后由 `resolve_struct_body` 填上——`agg->fields` 本身就是记忆化。

剩下的坑：

- **值类型自引用**（`next: Node`）会得到"大小无穷"，这是错误不是崩溃：字段类型
  解析完比一下 `ft == agg` 就报 `contains the struct by value`。
- `ty_size` / `ty_align` 各加一个 `-2` 哨兵（"正在算"）。真走到环上时 `ty_size`
  返回 -1（大小未知）、`ty_align` 返回 1，而不是把编译器栈打爆。
- C 那边**前向声明要先落地**：`typedef struct ZxS1 ZxS1;` 必须写在该结构体的
  字段处理**之前**。否则字段类型 `?*Node` 会先触发 `ZxOpt_pZxS1` 的 typedef，
  里面写着还没声明的 `ZxS1`。
- `ensure_type(TY_PTR)` 要递归注册元素类型——指针自己不占 typedef，但它指向的
  结构体得有名字。

## 26. `{any}`：用描述符驱动一份打印器

结构化打印最容易犯的错是"写两遍"：编译期路径按类型展开成 printf，运行时路径
再写一遍 switch——两边迟早分叉。所以只写**一份**：

每个用到打印的类型生成一个描述符：

```c
struct ZxAnyType {
    int kind;                 /* INT / FLOAT / STRUCT / TUNION / OPT / ERR / … */
    const char *name;         /* 聚合体名字，元组为 0 */
    int size, sign, n;        /* 值宽度 / 有无符号 / 字段或变体个数 */
    const ZxAnyField *fields; /* { 名字, offsetof, 成员描述符下标 } */
    int elem;                 /* 切片元素 / ?T、!T 的载荷 */
    int aux_off, aux_size;    /* 判别值偏移与宽度 */
    const long long *tags;    /* 枚举 / 联合体的判别值 */
    const char *const *names; /* 对应的变体名 */
    int is_str;               /* []u8：默认当字符串打 */
};
```

编译期路径直接 `zx_any_stdout(&zx_at[i], &值, mode)`，运行时路径在 `ZxFmtArg`
里带上 `ty` 指针，`zx_fmt` 遇到 `{}` / `{any}` 调同一个 `zx_any`。输出因此
不可能不一致。

细节：

- **偏移用 C 的 `offsetof`**，编译器不自己复算布局——省掉一份迟早会漂的布局代码。
- **字段表用下标互相引用**，整个 `zx_at[]` 一次性定义，所以递归类型
  （`Node` 里放 `?*Node`）不需要前向声明。
- **指针不跟进去**，否则 `Node{next: some(0x…)}` 会无限递归。深度也限 8 层。
- **取值的地址**用 `(T[]){ e }[0]`：C 里没有"右值的地址"，但数组复合字面量是
  左值，元素能用任意同类型表达式初始化。`(T){ e }` 不行——那是在初始化第一个
  成员，不是整个值。
- `{}` 与 `{any}` 的差别只剩两处：`[]u8` 加不加引号、枚举打不打名字。
  "默认打地址"对聚合值毫无信息量，所以默认就展开。

## 27. switch 穷尽性：一份判据，两处使用

穷尽性判定被两个地方需要：

- `check_switch`：switch 自身完不完整（**不管有没有人要它的值**）；
- `switch_ends`：函数会不会因此掉出末尾。

两处各写一份必然漂。抽成 `switch_coverage()`：给定 subject 类型和臂，算出
"要求哪些变体（want）"和"漏了哪些"。`want` 为空的 subject（整数）永远算穷尽，
`else` 一出现就直接算覆盖。

泛型实例化会把同一棵 switch 检查好几遍，报错按 (line, col) 去重——
和不可达代码那边同一个理由：`clone_tree` 之后同一句有两个指针。

## 28. 多序列 for：只报算得出来的长度

`for (a[0..], b[0..])` 的两段视图长度能不能算，取决于**基址**：

- `*[N]T` 的长度写在类型里 → N；
- 数组字面量 `&.{…}` → 元素个数；
- 切片（`[]T`）只有 ptr + len，长度是运行时的 → 不知道，不报。

然后减去下界（`[1..3]` 是 2）。算不出来的序列不参与比较——**宁可不报，也不误报**，
因为 `for (xs, 0..)` 这种写法里 `0..` 的长度本来就来自另一条序列。

## 29. 方法：一个普通函数 + 一个 `Self`

体里的 `fn` 不引入新实体。`Method { name, fn, fnty }` 只挂在 `Type` 上做查表，
函数本身还是那个 `NK_FN`，签名还是那个 `TY_FN`——**第一个参数就是接收者**。

这么定的原因：方法一旦变成"另一种函数"，后端就要多一套生成、编译器就要多一套
调用规则、`Type.f(p, a)` 这种显式写法就没法等价。现在 `p.f(a)` 在 sema 里只做两件事：

1. 把接收者补成第一个实参（`*Self` 接收者还要先包一层 `&`）；
2. 把 `n->inst` 挂到方法上，后端按普通函数调用生成。

`Self` 不作为关键字，而是 `resolve_struct_body()` 在体的作用域里预先放一个
`SK_CONST` 的 `Self`，值是 `ty_type(agg)`。这样泛型体里不用把 `T`、`cap` 重写一遍，
而且 `Self` 自动就是"当前正在定义的这个聚合体"——包括自引用的 `?*Self`。

接收者补地址检查了 `addr_ok`（IDENT / FIELD / INDEX / `*p`）。理由：`&` 只能作用在
左值上，而右值（`Vec{…}`、`f()`）在 C 里没有地址。错误在语义阶段报掉，不会漏到后端
变成一段编不过的 C。`*Self` 还额外要求绑定可变（`lvalue_mutable`），否则方法改了
一份拷贝还以为改到了。

报错按 (line, col) 去重（`mrecv_dup`）：泛型实例化会把同一段体检查好几遍，
不去重就是同一条错误打四遍。

## 30. 静态成员：布局要两遍

`const ZERO = Vec{ .x = 0, .y = 0 };` 写在 `Vec` 体里，它的初值要构造 `Vec`——
而这时 `Vec` 的字段表正算到一半。所以字段循环拆成两遍：

1. 先给每个成员占位（`it->index = k`），静态成员**只记位置，不碰初值**；
2. `agg->fields` / `agg->nfields` 挂好之后，再回头 `ensure()` 并回填 `fields[i].ty`。

两个相关的坑：

- 编译期求值遇到静态成员要**跳过**。静态成员的 `dflt` 就是它自己的初值，拿它去填
  默认值会无限递归（`ZERO` 的默认值是 `ZERO`，`ZERO` 的默认值是 `ZERO`…）。
  `ct_struct_lit()` 给静态成员写 `val_undef`。
- `val_init()` 也要跳过：C 结构体里根本没有这个成员，写进初始化列表会让后面的
  字段整体错位一格。

## 31. 泛型实参在 C 里没有变量

`List(i32, 3)` 的 `3` 是个符号，但它没有 C 变量——单态化时它就该消失。做法是给
`Symbol` 加 `ct_bind`，`specialize_raw()` 给前 nbind 个参数置位；后端遇到
`NK_IDENT` 时问 `sema_sym_has_storage()`，没有存储就把 `sema_sym_ct()` 的值
**直接内联成字面量**（`V_INT` / `V_FLOAT` / `V_BOOL`）。

第一版判据是 `!s->decl`（没有声明 = 没有存储），结果 `seqs.zx` 的输出乱了：
运行时形参同样没有 `decl`。判据必须显式打标记，不能从"缺什么"倒推。

**`Pending` 必须带作用域快照。** 泛型体里的方法要晚点才检查，而 `T`、`cap` 只活在
`specialize()` 里那个**栈上**的 `Scope` 上——函数一返回就没了。`snap_scope()` 复制
作用域链的结构（名字 → 符号，符号本体共享），`sema_check()` 用 `p->scope ? p->scope : &p->mod->scope`。
没有这一步的表现是方法体里 `cap` 报 `unknown identifier`。

## 32. 类型名跟着构造式走

`const P = Pair(i32);` 之后，这个类型叫什么？答案必须是 `Pair(i32)`，不能是 `P`。

原来的实现是在 `ensure_raw()` 里给 `s->type_val->name` 赋别名——于是同一个实例
在几处被起名时，最终名字取决于**谁的 `const` 先被检查**。那是巧合，不是名字；
`Pair(i32){a: 1, b: 2}` 变成 `P{a: 1, b: 2}` 只是让人看不出这是哪个类型。

改成从构造式反推：`name_type_from_call(call, result)`，在 `instantiate_type()` 末尾
和 `check_call()` 的类型构造分支都调一次。值参数用 `val_dump` 打出来，于是
`List(i32, 2)` 而不是 `List(i32, ?)`。

配套一个坑：`List(T, cap)` 里的 `cap` 会被解析成 `NK_TYPE_IDENT`（它写起来像类型），
但符号是 `usize` 值。`arg_ct()` 必须先 `lookup`，`ty != TY_TYPE && ct` 就按值取——
否则 `cap` 被当成类型，实例化的 key 变成一个新类型，无限套娃。

无限套娃有兜底：`specialize()` 外面包一层 `g_spec_depth >= 16`，报
`generic instantiation nests too deeply: '%s' asks for itself while it is still being defined`。
最典型的触发写法是方法接收者里重复写 `*List(T, cap)`——正确的写法是 `*Self`。

## 33. 匿名字面量：有期望类型就用它

`.{ .x = 1 }` 的类型从哪来？两个来源，按有没有期望类型分：

- `var v: Vec = .{ .x = 1 };`、`return .{ … };`、`f(.{ … })` —— 期望类型是 `Vec`，
  字面量**就是** `Vec`，字段按 `Vec` 的字段类型检查（这正是 R6 的用法）；
- `let anon = .{ .x = 1 };` —— 没有期望类型，它自成一个匿名结构体，字段类型由初值推。

不这么做的话，`var l: List(i32, 2) = .{ .buf = buf, .len = 0 };` 会报
``expected `List(i32, 2)`, found `struct{buf: *[2]i32, len: comptime_int}` ``——
字面量先自成一个匿名类型，然后才发现和标注不等。更糟的是字段类型被推成
`comptime_int`，连"能不能收下"都判断不了。

实现上 `check_lit_fields(n, t)` 是共用的一支：具名字面量 `Vec{…}` 从名字解析出 `t`，
匿名字面量从期望类型拿 `t`，之后的字段匹配、缺字段、联合体只准一个成员，逻辑完全一样。
编译期求值那侧也要跟上：`ct_struct_lit()` 原来只认 `n->a`（具名），现在回落到
`n->ty`，所以 `const one = .{ .name = "ann" };` 也能折成静态初值。

## 34. 枚举体的成员：另开一张表

`enum` 体里除了变体还能写 `const` / `var` / `fn`。**这些成员不能塞进 `fields`**。

`fields` 在这个编译器里已经是一门"变体表"，有四个地方按它遍历：`switch` 穷尽性、
`{any}` 的变体名、C 那边的枚举常量、以及 `(Color)5` 这种互转的合法性。往里面掺
`COUNT`、`name` 进去，穷尽性检查会要求你 `switch` 里写 `COUNT` 分支。

所以 `Type` 多了 `statics` / `nstatics` 两个字段（`Field` 数组，`is_static` 为真），
`ty_static_member()` 先查 `statics` 再回落 `fields[i].is_static`。方法表和学生 struct
共用 `collect_methods()`，一点没变。

配套两个小坑：

- **自引用**：`const FIRST = Color.red;` 写在 `Color` 体里，此时 `Color` 的类型还没算完。
  解法是 `ensure_raw()` 的 `state == 3`（外壳已挂、成员未填）分支也认 `NK_ENUM_TYPE`，
  并且 `check_expr` 的 `NK_IDENT` 遇到 `state == 3` 直接把外壳当类型值用。
- **编译期值**：`ct_eval` 的 `NK_IDENT` 原来只看 `sym->ct`，类型符号没有值。
  加一条：`ty->kind == TY_TYPE` 就返回 `val_type(sym->type_val)`，于是
  `Color.FIRST == Color.red` 能在编译期判定。

## 35. 方法与关联函数：靠第一参数的名字区分

`fn count() i32` 写在体里，它是方法还是"挂在类型上的普通函数"？语法上分不出来，
用**第一参数是否叫 `self`** 来分：

- 叫 `self` → 方法，`x.f()` 补接收者；接收者类型必须是 `Self` / `*Self` / `*const Self`；
- 不叫 `self` → 关联函数，只能写 `Color.count()` / `Ints.init(al)`，
  `x.count()` 报 ``is not a method (its first parameter is not `self`); call it as `Type.f(…)` ``。

`Method.has_self` 记下来，`check_field` 把它写进 `n->flag`，`check_method_call` 靠
`fld->flag` 判断。为什么不看签名里的类型是不是 `Self`？因为 `Self` 是体作用域里的
别名，`fn f(self: Self)` 与 `fn f(v: Self)` 在签名里长得一样——名字是唯一稳定的信号，
而且它跟 Zig 的约定一致。

## 36. `import`：只复制指向，不复制实体（v0.7 撤销关键字，结论保留）

> v0.7 删掉了 `import` 关键字（见 §39）。这条的**结论**原样成立——别名只复制指向、
> 不复制实体——只是载体从 `import {a} from "m.zx"` 换成了 `const a = m.a;`。
> 下面关于 `NK_IMPORT` 与"先绑导入再 hoist"的描述是历史机制，现在由 `ensure_raw`
> 里那条 `NK_FIELD` 别名分支 + `sym_link()` 承担。

`import {square as sq} from "lib/math.zx"` 落地时只做一件事：把模块作用域里那个
`Symbol` 的**字段逐个复制**到当前文件作用域（`sym_copy()`：decl / cname / ty / ct）。

于是：

- 函数体只有一份（在模块那一份 AST 里），`sq(3)` 生成的 C 名还是 `mathx_square`；
- 模块级 `var` 还是同一个 C 全局，不是副本；
- `let` / `const` 的编译期值一起复制过来，不需要"再算一遍"。

`import "x.zx";`（不带花括号）是另一种形态：它绑的是命名空间，名字取文件名去掉扩展名。
两种形态都能用，只是后者要写 `mathx.square(…)`。

顺序问题在 `hoist()` 里解决：**先**把 `NK_IMPORT` 全绑好，**再** hoist 其余顶层声明。
否则 `import {x} from "m.zx"; const y = x + 1;` 里 `x` 还没名字（R5 说声明顺序无关，
导入不能是例外）。重名、私有名字、不存在的名字都在绑定时报，一次性说清楚。

## 37. `std` 是真实模块，不是编译器里的一堆特例

一开始 `std.println` / `std.heap.page` 都是 sema 里的硬编码分支。加 `std.file` 时还好，
加 `std.ArrayList` 时就不行了——那是个泛型类型，泛型在 AST 里。

现在的形态：`std/std.zx` 是个普通模块（`module_load_std()` 按 `$ZX_STD` → exe 同级
`std/`、`../std/` → 当前目录找文件），`ArrayList` 就是里面的
`pub const ArrayList = fn (T: type) type { … }`。编译器只保留五个名字
（`print`/`println`/`format`/`heap`/`file`），由 `std_builtin()` 造符号、`sym_copy()`
**并进 std 模块的作用域**——于是 `std.println` 和 `std.ArrayList` 是同一条
"模块成员查找"路径，不需要两套逻辑。

`std/str.zx` 同理，由 `std.zx` 里的 `pub const str = module("str.zx");` 挂上去。
路径相对**引用者所在文件**，所以 `std/` 内部互相引用不受调用者目录影响。

顺手修掉的三个真 bug（都不是为了标准库打的补丁）：

- `*[]T` 被解析成 `*[N]T` 且 N 为空——`parse_type` 的 `TOK_STAR` 分支原来见到 `[`
  就吃，现在只在 `[` 后面**不是** `]` 时才当数组。
- 裸指针切片 `p[lo..hi]` 必须给上界（`*T` 没有数量），这是分配器回来的 `*u8`
  变成 `[]T` 的唯一通道。
- `undefined` 定型：`coerce_node` 遇到 `TY_UNDEF` 直接把节点类型改成期望类型；
  后端 `coerce()` 的 null/undefined 分支必须用 `ctype()` 而不是 `tn()`——`tn()` 只认
  聚合体，会把 `*T` 拼成 `ZxE<n>`。

还有一条纯语法判据的收紧：**只有 IDENT / TYPE_IDENT / FIELD / INDEX / CALL / CAST /
BUILTIN / MODULE 后面的 `(` 才算调用**。否则

```zx
if (p.len > 0) { … }
(p + 1).0 = v;
```

里那句换行写法会被读成"调用 `if` 的结果"。

## 38. 捕获名后面只能是块，或者单个返回值

`if (o) v` 这个形式里，`v` 是捕获名；`if (o) v + 1` 里 `v` 是表达式臂的开头。判据是：
`{` 开头是块、`IDENT {` 是捕获、`IDENT 二元运算符` 是"捕获 + 以它开头的表达式"、
`IDENT 值` 是"捕获 + 单个返回值"。

v0.6 曾给 `IDENT if/while/for/switch` 单独开一条判据，把 `v` 认成捕获名。那是在猜——
而且猜不对：`if (o) v if (v > 0) { … }` 里第二个 `if` 到底是分支体还是兄弟语句，语法上
两种读法都能通过，语义却完全不同（后者会先判断 `o`、丢掉结果，然后无条件判断 `v`）。

v0.7 改成直接报错：语句必须写进块里，`if (o) v { if (v > 0) { … } }`。
错误信息说明白要什么（``a capture name must be followed by `{ … }` or a single value``），
不再让读者对着缩进猜。

## 39. 没有 `import`：别名就是普通 `const`

v0.6 加过 `import {a, b as c} from "x.zx"`，v0.7 删了。理由不是它不好用，而是**它是多余的**：
它做的事就是"把那个名字绑到本地"，而 `const` 就是干这个的。

```zx
const heap = std.heap;        // 和 import 一个语义
const square = math.square;   // 顺便改名
```

实现上，`const X = <模块成员>;` 在语义检查时走 `sym_link`：不生成变量，直接把被指向那份的
`decl / cname / ty / ct` 拷过来，并打上 `ct_bind`（没有自己的 C 存储）。于是：

- **不要求 R1**。`const` 一般要编译期算得出值，但函数和类型根本算不出——别名豁免。
- **函数、类型、命名空间、常量一视同仁**。这是 `import` 做不到的：`import` 只能拿"声明"，
  拿不到 `std.heap` 这种命名空间值。
- **可以再导出一层**：`std.zx` 里 `pub const HashMap = map.HashMap;`，`std.HashMap` 就有了。
  用 `import` 的话得再造一条导出语法。

一个坑：`sym_copy` 会把 `is_pub` 也拷过来。别名导出与否应当看**别名自己那条 `pub`**，
所以 `sym_link` 先存后恢复——否则 `pub const HashMap = map.HashMap;` 会把源那份的可见性
带进来（或反过来被抹掉）。

## 40. 多 translation unit：共享头 + 每模块一个 `.o`

单 TU 的写法在只有几个文件时没问题，工程一大就成了"改一行重编全部"。v0.7 拆开：

```
prog.h           类型定义 + 运行时 + 跨模块原型
prog_main.c      入口模块
prog_<stem>.c    每个模块一份
```

三条取舍：

1. **类型定义放共享头**。同一份 AST 生成的定义必然一致，各单元看到的结构体布局相同。
   代价是每个单元都解析一遍类型定义；换来的是"加一个模块不用动别人的类型编号"。
2. **运行时辅助放头文件里，保持 `static`**。每个单元一份副本，各自内部链接，不会重复定义。
   没用到它的单元会有一堆未使用的静态函数——用 `-Wno-unused-function` 压掉即可。
3. **导出的函数/全局去掉 `static`**。名字本来就带模块前缀（`mathx_square`），不会撞车；
   原型和 `extern` 声明进头文件。

初始化也按模块切：顶层 `const` 里算不出来的那些，落在各自的 `zx_init_<stem>()`，
入口模块的 `main` 按依赖顺序（模块表倒序）依次调用。

增量判据用**生成物**而不是源文件：`prog_x.c` 内容没变就不重写，`.o` 就不会 stale。
所以改注释、改空白不会触发重编，改实现只重编那一个模块。`ZX_VERBOSE=1` 可以把
实际编了哪几个单元打出来。

## 41. `std.io`：编译器只给句柄原语，缓冲层写在库里

`std.file.read` 是整块读：`fseek` → `ftell` → 一次 `fread` 到分配器给的缓冲。
处理一个 1 GB 的日志时，"读一行"要搬一遍整个文件，这显然不行。

补的第一层是**句柄**：`std.io.openRead/openWrite/openAppend/read/write/seek/tell/close/flush`。
句柄就是装进 `usize` 的 `FILE*`，0 表示"没打开"，`close(0)` / `flush(0)` 是空操作。

关键取舍是**第二层放哪**：缓冲（一次读一块、按行切、行太长就翻倍）写在 `std/std.zx` 里，
不是编译器里。理由和 §37 一致——编译器只该提供"只有它能提供"的东西（syscall、指针、
内存布局），策略（缓冲多大、按什么切、超长行怎么办）属于库。这样改缓冲策略不用动编译器，
用户也能照着写自己的 `LineReader`。

代价是：编译器内建的命名空间（`std.file` / `std.io`）只能在 `std` 模块自己的作用域里
按名字用（`io.read(...)`），所以 `BufReader` 写在 `std.zx` 而不是 `std/io.zx` 里。
将来若有"子模块也能看见编译器内建"的机制，这一坨可以原样搬走。

`next()` 返回的切片**指向内部缓冲**，下一次调用就失效——复制是调用方的事。这是有意的：
逐行处理大文件时，绝大多数用法是"看一眼就扔"，每次复制反而更慢。

## 42. `@typeInfo` 的形状：宁可少四个字段，也别让 `.size` 截胡

`@typeInfo(T)` 返回的是**编译期值**，五个字段：

```
TypeInfo { kind: TypeKind, name: []const u8, bytes: usize, align: usize, fieldCount: usize }
```

三处非显然的决定：

1. **`bytes` 不叫 `size`。** `.size` 是语言自己的编译期字段（`len × @sizeOf(elem)`，§3），
   `ct_field()` 遇到 `.size` 会先算"容器有多大"再考虑字段。第一版叫 `size`，
   `@typeInfo(i32).size` 直接返回 48（`TypeInfo` 自己的大小）——不是 bug，是规则撞车。
   字段名让路，比改核心规则便宜。
2. **`kind` 是枚举，不是字符串。** 字符串在编译期只能比较"是不是同一段字面量"，
   想 `switch` 就得走 `std.str.eq`，而编译期不能执行 Zx 函数。枚举是整数，
   `switch (info.kind)` 天然能用。
3. **不返回字段表。** 遍历字段需要 `inline for`（按 `fieldCount` 展开），语言还没有。
   先给 `@hasField` / `@fieldType` 两个按名字查的入口——泛型里 90% 的用法是
   "有就取、没有就走默认"，这个组合够用；等 `inline for` 落地再补 `fields`。

附带修掉的两个真问题：

- **模块作用域的"快照"会冻结符号表。** `schedule_body()` 给待检查的函数体存了个作用域快照，
  `snap_scope()` 深拷贝到模块级时把 `first` 指针冻在那一刻。编译器内建（`print`/`io`…）是
  `std.zx` 解析完、所有函数体都排好队之后才并进 std 作用域的——于是 `std.zx` 自己的函数体
  一个内建都看不见（以前没人用到，所以没暴露）。现在模块作用域标 `is_module`，快照直接引用
  同一个 Scope，后加的名字立刻可见。
- **`@typeName(@typeOf(x))` 打印出 `type`。** 后端取的是 `items[0]->ty`（外层那个 `@typeOf`
  节点的类型，永远是 `type`），而不是语义层算好的 `n->str`。改成优先用 `n->str`。

另外后端多了一条通用规则：**折叠过的标量按字面量发**（`ex()` 里对 `NK_FIELD` 先看 `n->ct`）。
否则 `@typeInfo(T).align` 会被发成"读一块全零描述符的字段"，静静地得到 0。

## 43. inline for：展开的是克隆，不是循环

`inline for (0..N) i { … }` 的实现只有一句话：**语义层把循环体克隆 N 份，每份把绑定
换成一个编译期常量**（`SK_CONST` + `ct`），后端逐份发射、每份包一层大括号。没有循环，
没有运行时表示——`i` 甚至能当数组长度用（`var buf: *[i + 1]u8`），因为它是货真价实的
编译期值。

三个决定：

1. **克隆，不共享。** 每一份都是独立的节点副本（和泛型单态化同一套 `clone_tree`）。
   这不是浪费：编译期执行会把中间值烙在节点上（`ct`），共享节点等于让第 k 份看到
   第 k-1 份的残值。
2. **没有 `else`，不参与标签。** 每份都执行，"正常跑完"没有意义；没有运行时循环
   可供跳出，收割也没有目标。`continue` / `return` 照常作用于外层。
3. **绑定可省。** `inline for (0..3) { … }` 就是纯重复；普通 `for` 的绑定仍然必填。

### 43.1 这轮逼出来的三个真 bug（都是"编译期值烙在真实节点上"）

写 `inline for` 的过程中，`returns.zx` 的 `spin()` 突然把 `if (n > 100) return n;`
剪成了裸 `return n;`，`jumps.zx` 的 `hit` / `got` 全错。根因是同一个：

**编译期执行真实 AST 会把"最后一轮的值"烙在节点上。**

- **检查期折叠不执行语句。** `while` 作为"表达式形式"的语句走 `check_expr`，末尾的
  `fold()` 对整个 WHILE 节点做 `ct_eval` → `ct_run` 把真实循环在编译期跑起来，撞到
  迭代上限时最后一次 `n > 100`（n=101）= true 被缓存到真实条件节点，后端照着剪。
  修法：`fold_expr()` —— 检查期只折值表达式，语句一律不执行。const 初始化器的
  编译期求值走 `ensure → fold`，块值在那里合法，不受影响。
- **const 初始化器折叠完要擦烙印。** 局部 `const hit = search: for …` 按规则 R1 必须
  编译期算出——这个执行是合法的，但循环里 `a*b == 6` 在 yield 那一轮的 `true` 会留在
  真实节点上。修法：`s->ct` 拿到最终值后 `ct_clear` 整棵初始化子树（根上的留着——
  顶层 const 的静态物化要读 `d->b->ct`）。
- **后端剪 if 只认语义层的标记。** 以前后端看到 `cond->ct` 是 V_BOOL 就剪另一臂；
  上面两条修完后，真实节点上仍可能有**合法的**烙印（`ensure` 路径），但它们只对
  编译期成立。修法：`check_if` 在"条件是编译期常量且 `ct_pure`（不读 var / 参数 /
  捕获）"时给 IF 节点打 `flag`，后端只认这个标记。语义决定能不能剪，后端只执行。

一句话总结：**编译期执行的产物只允许出现在两个地方——克隆出来的树，和符号的 `ct`。
真实 AST 节点上的 `ct` 只在语义层明确祝福（纯编译期表达式）时才存在，后端使用前
必须核对祝福标记。**

## 44. 统一分配 API：申请的都是数组，返回的都是数组指针

旧规则 R9 有一条隐式魔法：`var buf: *[64]u8 = undefined;` 会"额外申请 64 字节"。
问题不在行为而在**不可见**——分配点是源码里搜不到的，`undefined` 这个词也完全没
表达"我要内存"。v0.10 起改成显式 API，三个决定：

1. **`undefined` 不再分配。** `var x: *[N]T = undefined;` 只是"指针槽不初始化"
   （后端发 `T *x = 0`，误用撞空指针而不是悄悄改栈）。要内存就写
   `std.stackAlloc(T, N)` / `std.heapAlloc(alloc, T, N)`——分配点是一行可搜索的
   源码。模块顶层的 `undefined` 保留静态分配（顶层没有栈帧，也没有更好的去处）。
2. **两个 API、一个形状。** 都返回 `*[N]T`：`stackAlloc` 的 N 编译期已知（结果类型
   带长度），后端发 `__builtin_alloca`，存储活到函数返回（和 Zig 的栈分配一个语义，
   循环里每轮是新的一块）；`heapAlloc` 显式传分配器（§13 的约定），穿过 `alloc`
   函数指针，OOM 直接 abort——结果是非可选的数组指针，没有失败路径，要"可能失败"
   就自己走 `alloc.alloc(bytes)` 的 `?*u8`。
3. **栈/堆不用类型区分。** 栈/堆之别是生命周期问题，不是类型问题；区分来源会污染
   所有泛型，切片化时信息也天然丢失。需要硬保证的那一条——**不许把指向当前栈帧的
   指针 return 出去**——用逃逸检查直接在编译器里强制。

### 44.1 逃逸检查的实现面

`expr_frame(e)` 判定"e 的值是否指向当前栈帧"，`addr_frame(o)` 判定"&o 是否指向
当前栈帧"，只在 `return` 处消费。栈帧来源四种：局部变量的槽位（符号记 `in_fn`）、
`&.{…}` 匿名存储（节点形态即答案）、`std.stackAlloc` 调用（节点记 `esc`）、以及
它们的字段 / 下标 / 指针运算（结构递归）。两个关键细分：

- **取地址跟被指物走。** `&p.f`（p 是指针）：地址在被指物里，不算逃逸——所以返回
  `&self.field` 这类方法惯用法照常工作；`&s.f`（s 是局部结构体值）：地址在 s 的
  槽位里，算逃逸。判定靠操作数的**类型**（指针/切片 → 看被指物，聚合 → 看槽位）。
- **值经局部变量中转也能追。** 符号记 `stack_val`（初值或最近一次赋值来自栈帧
  表达式就置位，永不复位——宁误报不放过），`var p = std.stackAlloc(...); return p;`
  同样被拦。

已知保守面：栈指针存进聚合体字段再整体取出来追不到——宁漏勿误报。这个检查管住
的是"最容易踩的坑"（返回栈缓冲），不是完整的生命周期分析；后者不在 Zx 的取舍里。

## 45. fields 元表与纯编译期类型；std.process

**fields 的表示是"切片视图"。** `info.fields` 在编译期值里是一个 `V_PTR`（指向
一块 `V_AGG` 数组值，`nitems` 记长度）——`.len` / 下标 / 切片在 `ct_eval` 里
走 `ct_view_len` / `ct_index` 那条既有路径，不用新机制。元素是
`std.FieldInfo = struct { name, ty }`：字段叫 `ty` 而不是 `type`，因为 `type`
是关键字当不了字段名。`f.ty` 在 `check_field` 的 TY_STRUCT 分支里把折叠出的
`V_TYPE` 挂到节点的 `type_val` 上——这样 `@typeName(f.ty)`、`eql(f.ty, x, y)`
这类"字段值当类型用"直接成立。

**TypeInfo / FieldInfo 是纯编译期类型（§45.1）。** FieldInfo 里装着一个 `type`
值，C 里没有对应物；把整个 TypeInfo 物化成运行时变量只会得到一块全零。所以：

- 语义层：`var x: std.TypeInfo` / `x: std.FieldInfo`（含切片/指针/可选包裹）
  在局部声明、全局声明、参数三处直接报错——引用它们就用
  `const info = @typeInfo(T)`，让值折进常量；
- 后端：万一有没折干净的引用（比如 `switch (info.kind)` 折了条件没折 case
  标签），跳过物化但仍给字段类型发 typedef（TypeKind 枚举），免得 C 报
  undeclared。

**`@typeName(f.ty)` 的投机解析坑。** `@` 内建的实参走投机类型解析
（`@intCast(T, x)` 需要），`f.ty` 会被吃成 `TYPE_IDENT(f).ty`，而 `f` 是值——
报 "'f' is not a type"。修法在 `check_field`：base 是 TYPE_IDENT 且查到的符号
不是类型时，把节点还原成普通 IDENT 再走值检查。顺带修了类型语法的点路径
（`std.HashMap` 现在能直接写在类型位置——以前只有 `const H = std.HashMap` 别名
一条路），副作用是 `resolve_type` 的 TYPE_IDENT 分支现在会把 `sym` 挂上节点。

**std.process 的 argc/argv 走"预扫描 + 外部全局"。** main 的签名必须在发函数体
之前定，而"用没用 std.process"通常发体时才知道。办法：代码生成前把整棵 AST
扫一遍认 `std.process` 访问形状（别名 `const p = std.process` 也能认出，因为
扫描认的是创建点）；用到就给 main 加 `(int argc, char **argv)` 参数，把值存进
两个外部链接的全局量（运行时辅助在共享头里只有 extern 声明，定义在入口单元，
每单元一份 static 会变成多份定义）。运行时按需懒发射：`args()` 惰性把 argv
打包成切片数组（argv[0] 不算，和 Zig 同语义）、`getEnv` / `setEnv` 把 Zx 切片
拷进 NUL 结尾缓冲再调 CRT（Windows 走 `_putenv`）、`exit` 直接 `exit()`。
返回 `[][]const u8` 和 `?[]const u8` 全靠既有类型描述符机制，运行时里没有
任何硬编码的 C 类型名。

## 46. std.io.print：句柄流的格式化输出

`std.print` 只认 stdout，而 `std.io` 的句柄（文件、`stderr()`）只能裸
`write` 字节。M18 补上 `std.io.print(h, fmt, args…)` / `std.io.println(h, fmt, args…)`：
语法和 `std.print` 完全一致，落点是任意句柄（`usize`，里面装 `FILE*`）。

**一律走运行时解析器，不做编译期拆段。** stdout 的 `std.print` 在格式串是常量时
拆成一串 `printf`（零解析）；句柄流不做这个优化，全部发成一条
`zx_fmt_out((FILE*)(uintptr_t)(h), fmt, args, nargs, nl)`。三个理由：

1. **句柄只求值一次。** 编译期拆段的话 `FILE*` 得在每段重复出现——
   `io.println(io.stdout(), …)` 里的 `stdout()` 就会被调用 N 段次。
2. **输出不可能分叉。** `zx_fmt_out` 本来就是 `std.print` 运行时路径的
   落点（签名带 `FILE*`，stdout 只是恰好常传的那个），两条路径共用同一套
   `zx_fmt`，同一格式串的输出逐字节一致是结构保证，不是对齐出来的。
3. **代价可忽略。** 文件 I/O 的开销面前，一次格式串解析不值一提。

sema 端照旧在编译期把能查的都查掉：`check_fmt_args` 校验占位符个数、下标
越界、动词与实参类型——运行时解析器只是再兜底一遍（和 `std.print` 的运行时
路径同一约定，spec §11.1 第 3 条）。

**识别靠符号，不靠拼写。** 第一版按 `std.io.print` 的两层 FIELD 拼写识别，
立刻被最自然的写法打脸：`const io = std.io;` 别名之后 `io.println(…)` 就
不匹配了。改法：给符号挂 `BI_IO_PRINT`（sema 判这个）和 cname
`zx_io_print` / `zx_io_println`（后端判这个）。别名 `sym_link` 会把
`builtin` / `cname` 一起复制过来，所以 `std.io.print` 和别名拿到的是同一份
识别依据。check_call 在 callee 查完、符号挂上节点之后再按 builtin 分派，
变参形态不需要普通函数类型。

教训一条：`zx_fmt_out` 的实参个数抄 `ex_format` 时抄成 `nitems - 3`，
少了一个——fmt 自己占的下标不同（`std.format` 是 1，`io.print` 也是 1，
实参都从 2 起，个数都是 `nitems - 2`）。这类错位 C 只给 warning，测试
第一轮就抓住了。

## 47. if 的单语句臂；ArrayList 补全；ct_call 复检的幂等坑

**`if (c) return x;` 不加花括号。** 之前只有表达式臂能省花括号，`return` /
`continue` / `defer` 必须写块——一个只有 return 的分支要写两对花括号，噪音太大。
v0.13 放行这三个关键字：解析时把语句包进一个单语句块，后续语义/后端零改动。
为什么只放这三个：`if` / `while` / `for` / `switch` 放在捕获名后面会产生
"分支体 vs 兄弟语句"的真歧义（`if (u) v if (c) {…}` 两种读法都成立），
`return` / `continue` / `defer` 不会——它们之后不可能再接一个"同层的 if"。

**ArrayList 补全。** `first/last/insertAt/removeAt/reverse/resize/swap`。
`insertAt` 先 reserve 再整体右移（`i == len` 等价 push）；`removeAt` 左移
（删末尾等价 pop）；`resize` 变长用 fill 补、变短直接截断、容量不动。
仍然**没有** `remove(v)`：泛型里没有"元素相等"的约束（语言没有 trait），
按值删要么要求元素是可比较的，要么把比较函数传进来——两者都不值得。
要按值删就 `indexOf` 自己写循环 + `removeAt`。

**顺带修掉一个既存 bug：`ct_call` 复查已检查过的函数体。**
编译期折叠对函数的调用时，`ct_call` 会 clone 一份函数体再 `check_block`
一遍（为了让 ct 解释器跑的是有类型的树）。但 clone 拿的是**已经检查过**的树：
方法调用第一次检查时已经把接收者塞进了参数表（`nitems 1 → 2`），克隆体
带着这个改写后的形状再 check，`check_method_call` 就把接收者又数了一遍，
报 "method takes 1 argument(s), 2 given"。
触发条件很窄：函数体里有"在局部结构体值上调方法"，且这个函数被编译期折叠。
测试套件里没有这样的组合，所以一直没暴露——写 demo 才撞上。
修法：Node 加 `meth_done`，改写完成后置位；`check_method_call` 看到它就
直接返回方法类型，不再补接收者。clone_tree 是浅拷贝整个 Node，标记会跟着走，
克隆体因此天然幂等。回归用例：`tests/good/method_fold.zx`。

## 48. 数值语义：回绕是定义行为，trap 是唯一例外（M19）

这一条在写下第一个实现之前就该定，因为它发布后改不动。

**整数回绕。** `+ - * <<` 按**目标类型的位宽**回绕，不做 UB 留给 C。后端
统一发成"先转无符号算、再转回有符号"（`((i32)((uint32_t)a + (uint32_t)b))`），
因此 `-O0` 和 `-O3` 一致——C 的有符号溢出是 UB，直接发 `a + b` 在优化下会被
当成"不会溢出"从而改写控制流，这正是"在 C 之上做语言"最容易踩的坑。
复合赋值（`+= -= *=`）走同一套发射函数，不重复实现。

**除零。** 编译期可见就编译错（`10 / 0` 折叠时报错）；运行时发
`zx_div0()`：`fprintf(stderr, "zx: division by zero")` + `abort()`。
不用 C 的 `/`：那同样是 UB，而"崩掉且说明原因"是可诊断的行为。
`iN` 的 `MIN / -1` 单独处理（回绕成 `MIN`，不 trap）——它溢出但不除零，
按回绕处理保持一致。

**移位。** 右操作数先按位宽掩码（`n & (bits-1)`）。C 里移超位宽是 UB，
这里把它定义成"循环计数"式的行为，代价是一句 `&`。

**浮点。** 按 IEEE-754 走：除零得 `inf`，`0.0/0.0` 得 `nan`。编译期的浮点
除法早期是"除零报错"，与运行时不一致——改成也走 IEEE，两条路径不许分叉。
浮点 → 整数的越界转换**仍未定义**（已知缺口，写进规格的 R10 里明说）。

**字面量拟合。** 之前 `let a: i8 = 300;` / `let b: u8 = -1;` 都静默截断，
这是最恶劣的一类 bug：编译通过、运行出错误答案、没有任何提示。现在在
`check_expr` 的整数字面量分支 + `coerce_node` 两处做范围检查（后者堵住
结构体字段、函数实参这些 expect 不一定传到的路径）。
例外只有一个：类型最小值。`-170141183460469231731687303715884105728`
里的正数字面量是 max+1，只有在**紧跟一元 `-`** 时放行——用 `g_neg_lit_ctx`
静态标志传递这个上下文（检查是单线程递归的，安全）。

**表达式不查。** `let x: i8 = 100 * 2;` 得到 `-56` 而不是报错——因为 R10 说
"编译期与运行时同宽同回绕"，如果折叠时用任意精度再判越界，同一个表达式在
编译期和运行时会给出两个答案。要在编译期抓溢出，请用更宽的类型。

**128 位全链路。** `i128`/`u128` 之前只有类型和后端映射，字面量超 u64 直接
静默变 0（值模型只有 u64 + neg）。补的方式：`Value` 增加 `hi` 字段（绝对值的
高 64 位），`val_big128` 从十进制文本切分；后端用 `((unsigned __int128)hi << 64
| lo)` 发射，**负数发二补码位模式**（`-mag mod 2^128`）——"先转有符号再取负"
在 `INT128_MIN` 上是 UB。打印：`printf` 没有 128 位动词，改成先转十进制
字符串再 `%s`；`ZxFmtArg` 加 kind 9/10 走同一条路。还有一个坑：**没有类型
标注的超大字面量**（`println("{}", 170141183460469231731687303715884105727)`）
类型是 `comptime_int`，早期走 64 位打印路径，输出 `-1`（低 64 位全 1）——
判断条件从 `TY_INT && bits==128` 扩成"或 comptime_int 且值确实超出 64 位"，
小字面量仍走 `%lld`，保住 `{:x}` / `{:b}` 的原有行为。

## 49. 增量编译的缓存不能只靠 mtime

`test.sh` 长期有"偶发假失败"：同一套用例连跑，失败的文件随机漂。根因不是
测试脚本，是驱动层的 `.o` 复用判据——`o < fmtime(c)` 是**秒级**比较，而
测试在同一秒内重写 `.c`，新旧看不出差别，于是上一轮的 `.o` 被当新鲜的复用，
跑出旧二进制。

修法：`write_file_if_changed` 返回"内容是否变了"；变了就直接 `remove(opath)`，
不参与时间戳比较。共享头变了则作废所有模块的 `.o`。这条同时保住了原有的
增量收益（内容没变 → 不动 `.c` → 不动 `.o`）。

体会：时间戳精度是环境属性（文件系统、时钟粒度、并行度），不能拿它当
正确性判据；内容比较是精确的，代价只是多读一遍文件。

## 50. if 臂允许是单条表达式语句：分号归谁

v0.13 只放行了 `return` / `continue` / `defer` 当臂。写真实代码时最常撞的却是
另一条：`if (c) doA(); else doB();`——明明每边只有一句，还是得写两对花括号。
v0.15 把「一条表达式语句」也放行。

**分号归臂，不归外层语句。** 难点全在这里：`let x = if (c) a else b;` 的那个
分号是声明语句的，`if (c) f(); else g();` 的 then 臂分号却是臂自己的。判据只有
一条——**分号后面紧跟 `else`**：

- `;` + `else` → 语句形态的臂：吃掉分号，把臂包成单语句块，继续解析 else；
- 其余情况 → 分号归外层，行为与 v0.13 完全一样（`if (c) f();` 照旧）。

因为这个判据挂在「then 臂」上，值形态自动免疫：`let x = if (c) a else b;` 的
then 臂后面跟的是 `else` 而不是分号，走的仍是表达式臂那条路。else 臂的末尾分号
不再由 `parse_if` 吞——留给 `parse_stmt` / 声明去收，于是
`let y = if (c) f(); else g();` 报的是「void 不能当值用」那一类错，而不是
莫名其妙的「缺分号」。

一个附带的洞：标签语句路径（`lbl: if (c) f(); else g();`）直接
`return parse_construct(...)`，不经过 `parse_stmt` 末尾的 `accept(TOK_SEMI)`，
所以那里补了一次分号接收。这种写法很少见，但不补就是一条无谓的解析失败。

没跟着放开的：`if (c) { … }` 里的**多条**语句仍然要写花括号；`if` / `while` /
`for` / `switch` 这类会引出嵌套控制流的语句仍然不能当臂（v0.13 的理由不变：
`if (o) v if (c) { … }` 有两种读法都能成立）。赋值没有歧义（Zx 里赋值是表达式），
所以 `if (c) x = 1; else x = 2;` 天然能用。

## 51. 诊断：码是契约，措辞不是（M22）

**为什么要有码。** 错误信息是给人读的，措辞会为了更准确反复改（"has no member"
改成 "has no field" 就更准确）。如果测试断言的是措辞，每次改文案都要改一堆
用例，改文案的成本高到没人愿意改；如果断言的是码，文案随便改。所以：
**码稳定，消息自由。** 已发布的码不改含义，新增在段内递增。

**码怎么分派。** 91 处 `err_at` 调用点，逐个加参数不现实，也不该让"码"散落在
91 个地方。做法是在 `zxc.c` 里一张表：消息片段 → 码，第一条命中即用，命中不了
按阶段给默认码（E01xx/E02xx/E03xx）。代价是片段匹配有点"猜"，所以表里**先写
最具体的**（`division by zero` 在 `compile time` 之前，`format specifier` 在
`needs` 之前）。

有一个坑值得记下来：语义层也有 `expected \`i32\`, found \`[]const u8\`` 这种
形状的消息，它是类型错（E0301），但会被笼统的 `expected`（E0201）先吃掉。
解法是把 `found \`` 这条规则放在 `expected` 前面——**顺序就是优先级**。
解析器则干脆不查表：`perr` 自己定 E0201/E0202，因为它比任何片段匹配都清楚
自己在报什么。

**多错误恢复。** 语义层本来就能继续（每条语句独立检查，错类型用 `<error>` 吸收）。
真正缺的是解析器：顶层循环解析完一个声明，如果这一轮里多了错误，就同步到下一个
`fn`/`const`/`struct`/`enum`/`union`/`pub`/`module`（括号深度 0 才算），然后继续。
之前 `fn c() void` 漏一个 `{`，后面的 `fn main` 会被当成坏声明的尾巴整段吃掉。

**上限 30 条。** 一个语法错能连出几十条级联。全打出来反而把第一个错（通常是
根因）挤出屏幕。超过上限只计数不打字，结尾 `zxc: N error(s) (first 30 shown)`。

**有语法错就不进语义检查。** 语法树不完整，语义错基本都是噪声。rustc 也这么干。

## 52. extern "C"：最小 FFI 的边界在哪里（M23）

目标只有一个：**让标准库从"自己写"变成"能借"**。所以不追求完整的 FFI，
而是把"能调 libc"这条最短路径打通，把做不到的写清楚。

**语法选 `extern fn` 而不是 `extern "C" fn` 为主。** 现在只有一种 ABI，字符串
是纯粹的仪式；但保留 `extern "C"` 这个写法（写成别的直接报错），因为将来若真要
接别的 ABI，语法位置已经在那儿了，不会又是一次破坏性改动。

**符号名原样，不转义、不加前缀。** 这一步踩了两个坑：

1. 后端有个 `cname()` 会给 C 关键字和头文件里的公共名字加下划线后缀（`puts` →
   `puts_`），目的是避免和 include 进来的 stdio 撞车。对 Zx 自己定义的函数是对的，
   对 extern 就致命——`puts_` 链接不到。所以 extern 走独立的名字发射路径。
2. 语义层给顶层名字加模块前缀（`mathx.add` → `mathx_add`），extern 也不能加：
   它指向的是别人编好的符号。

**标准头已经声明过的名字不重复发原型。** `malloc` 在 C 里是 `void* malloc(size_t)`，
我们按 Zx 类型发 `char* malloc(uint64_t)` 就是冲突类型，直接编不过。这些名字
（`libc_declared()` 那张表）跳过原型，用头里的声明；调用点仍按 Zx 签名转换。
代价是"用户写的签名和 libc 不一致时，错误来自 C 而不是我们"——可以接受，
C 的报错在这里足够清楚。

**`*u8` 在边界映射 `char*`。** Zx 没有 `char`：一个字节就是 `u8`，字符串是
`[]const u8`。而 libc 的字符串函数收 `const char*`。两种选择：给语言加一个
`char` 类型（大工程，且 C 的 `char` 符号性还是实现定义的），或者在 FFI 边界上
把"指向 u8 的指针"写成 `char*`。选后者，并且在调用点显式转型，编译警告清零。
这条只影响 extern 原型，Zx 内部的 `*u8` 依旧是 `uint8_t*`。

**不做的**：变参（`printf` 直接调）、C 宏、回调约定验证、结构体按值传的 ABI
细节。都在规格 §18 里明写——"不能做什么"和"能做什么"一样是规格的一部分。

## 53. 测试 runner 用 Zx 自己写（M24）

`test.sh` 从 200 行 shell 降到 60 行包装，真正干活的是 `tools/runner.zx`。
理由不是"自举好看"，而是两条具体的：

1. **测试脚本也该被类型检查。** shell 里的错误是运行到一半才炸，而且每加一条
   断言就要动一次引号转义；换成 Zx 之后写错字编不过，字符串拼接也不用转义。
2. **它是语言的一次真实压力测试。** runner 覆盖的恰好是"最常被使用"的那条路：
   读文件、切字符串、拼命令、起进程、收输出、比对。这些地方一有缺口就当场暴露，
   比写十个 hello world 有用——本轮就从里面挖出三个真 bug（见下）。

**顺带定下的两条工程规则**（都是被 runner 逼出来的，与语言语义无关，
但会影响所有在 Windows 上跑测试的人）：

- **`system()` 传命令要自己多包一层引号。** 它是 `cmd /c <整串>`，而 cmd 在
  命令以 `"` 开头且引号总数不是「恰好两个」时会剥掉最外层的一对。
  于是带引号的路径 + 引号重定向被剥坏，报「文件名、目录名或卷标语法不正确」。
- **诊断必须在出口去重。** 语义检查对同一个表达式可能求值两次（定型一次、
  常量折叠一次），而求值是带副作用的。与其在每个求值点打补丁，不如在
  `diag_emit` 里按「位置 + 码 + 文字」判重——**用户看到的条数必须等于
  摘要里的数字**，否则 `// expect-count:` 这类断言就没有意义。
  新增 `tests/bad/div-zero-dedup.zx` 守住这条。

**关于测试布局的一条约定**：`tests/**/` 下被 glob 直接扫到的必须是"根文件"
（自己就是一个完整用例）。配套模块一律放子目录——`tests/multi/<name>/main.zx`、
`tests/bad/priv/priv-util.zx` 都是这个形状。这样"什么算一个用例"由目录结构决定，
不需要在脚本里维护例外名单。

## 54. 带标签联合体的标签、以及标签作用域的完整性（M25）

自举评估顺带挖出两个**静默错误**——编译不报错，程序跑出错误答案。这种 bug 的
优先级高于任何功能：错误答案比崩溃更难发现。

**① 联合体字面量必须写出 `.tag`。** `U{ .b = 7 }` 原来生成
`((U){ .u.b = 7 })`，C 的指定初始化把标签零填成第一个成员，于是
`switch (u.tag)` 永远走第一个分支。根因是后端判断条件写成了"载荷类型是
`{tag, T}` 元组"，而 sema 早已把载荷解析成纯载荷。规则定死：**带标签联合体的
每一个成员都必须有标签**（没有就在构造点报错），生成的 C 必须显式写 `.tag`。

**② 标签加在 `if` 上时，作用域必须由 `if` 自己建。** 规格 §8.1 把

```zx
let sign = s: if (x > 0) { s: 1; } else { s: 0; };
```

标为**推荐写法**，但后端只为"臂上的标签"建作用域，`if` 自己那一层漏了。
`NK_YIELD` 在 `lab_find` 里找不到目标时**静默 return**——两个臂变成空的，
函数返回 0。这条比上一条更严重：Zx 删掉了 `break`，"收割"是唯一的值出口，
出口坏了等于控制流地基裂了。

**顺带定下一条**：`NK_YIELD` 找不到目标时应当**报内部错误**，而不是静默丢弃。
"没人接的收割"在任何情况下都不是合法程序。

**这两个 bug 活到现在的原因值得记一笔**：标签化联合体和"标签 if"都是规格里
写得最漂亮、用例里覆盖得最少的地方——`tests/good` 里恰好没有一条用例真的
`switch` 到第二个成员，也没有一条把标签加在 `if` 上。**规格写得对不对，
只看有没有用例真的踩上去。** 回归：`tests/good/union-tag.zx`、
`tests/good/label-if.zx`。

## 55. 自举：先补语言缺口，再搬前端（M25）

评估结论写在 `spec/bootstrap.md`。要点：

- **表达力够用**。`tests/good/selfhost.zx` 是一个真跑起来的小型词法器 +
  递归下降求值器，递归类型、带标签联合体、方法互递归、HashMap 关键字表、
  深递归全部实测通过。没有一条是"Zx 根本写不出来"。
- **前端 ≈ 2400 行 C**，估计用 Zx 写 3000–3500 行（+25%~45%）。膨胀来自两个
  缺口，不是能力不足。
- **两个值得改语言的缺口**：没有 `orelse` / `.?`（每访问一个可选子节点都要
  写 helper，AST 遍历代码翻倍）；char 字面量不能做 switch 模式（词法主循环
  只能写 `switch ((i32)c) { 48, 49, … }`）。
- **一个不改的**：没有 `break`。前端 37 处 `break` 换成 `label: while (…)`
  的收割写法即可，而且收割能带值，比 `break` 更强。

**顺序建议：先做语言缺口，再搬前端。** 理由不是保守，而是收益面：`orelse`
和 char 模式的收益是全局的（所有 Zx 代码都变短、变能读），自举只是其中一项。
反过来先搬 3000 行、再发现"每天都想写 `orelse`"，改动成本就高得多。

**自举成功的三条硬指标**：158 项回归全过；自举后的 `zxc` 能编译
`tools/runner.zx` 且结果一致；全量编译时间不超过现在的 2 倍。

## 56. union(enum)：变体名即枚举，布局统一为载荷在前（M27）

M25 的自举评估确认了表达力之后，联合体成了最明显的手写噪音：每个变体都要
先声明一个标签枚举、再写一遍 `{Tag.variant, Payload}` 元组。`union(enum)`
把这件事收进编译器。

**实现走的是"糖到底"路线**：解析器只记一个 `op=1` 标记，sema 在
`resolve_struct_body` 里合成一个隐式 `TY_ENUM`（变体按声明顺序取
`0..n-1`，底层类型默认 u32、可用 `union(enum(u8))` 指定），给每个变体
打上 `has_tag/tag`。之后 `.tag` 访问、`.u.成员` 载荷、构造时写标签、
switch 穷尽性检查、`{}` 打印——全部复用显式标签联合体已有的机制，后端
对糖零感知。不新增任何发射路径，是这次改动最省的形态。

**一个值得记的坑**：糖分支必须排在旧式 `{标签, 载荷}` 元组检测**前面**。
`rect: {f64, f64}` 的载荷本身就是元组——旧式检测看到二元组就抢先命中，
把载荷当成了"标签 + 载荷"，rect 悄悄没打上标签，switch 直接报
"has no variant 'rect'"。教训同 §54：类型位置的 `{a, b}` 有两种身份
（元组类型 / 标签元组），靠语法猜身份迟早踩空，糖的分支顺序就是消歧。

**布局统一为载荷在前、标签在后。** §5 早就承诺 `?T` 是 `{值, ok}`，
但带标签联合体生成的 C 是 `{tag, union{…}}`——同一份规格两种布局方向。
v0.18 把带标签联合体（显式和糖）统一成 `{union{…}, tag}`，与 §5 对齐。
现有四个用例（any / methods / returns / selfhost）语义不变、输出逐字节
一致——访问器和构造都是编译器生成的，用户代码对布局无感。

**顺手不做的**：`switch (s)` 直接分派（Zig 的 `.a => |v|` 捕获形态）——
需要把 switch 的模式匹配对象从"枚举值"扩展成"联合体值"，和现有捕获
机制（§8.1）的交互要重新想，值得单独一轮。`void` 载荷也不支持：C 的
联合体不允许 void 成员，零尺寸成员要等布局层有"空载荷"特判，等真有人
写出来再说。

## 57. `orelse` 与 `.?`：给可选值两个出口（G1）

自举评估把"没有 `.?` / `orelse`"排在缺口第一位（§55、`bootstrap.md` G1）。
理由不是"Zig 有所以我们也要有"，而是**写 AST 遍历时每个子节点都是 `?*Node`**：
没有这两个出口，每次下降都要写成

```zx
if (n->a) x { use(x); } else { report(); }
```

一个三行的方法膨胀成十行，而且"失败怎么办"被强行塞进同一个形状里。
补上之后同一个意思写两遍就够：`n->a.?`（必须有）/ `n->a orelse fallback`。

**`orelse` 是关键字，不是运算符表里的符号。** 它只有一个优先级——高于赋值、
低于 `||`；右结合。写成运算符就得在优先级表里给它找个位置，而它的语义是
"取个值回来"，和布尔/算术都不该比黏度。语法上它出现在二元运算的位置，
解析器只多做一件事：造 `NK_ORELSE` 而不是 `NK_BIN`（它要短路，不能当普通
二元运算发）。

**右边必须惰性。** `x orelse expensive()` 在 `x` 有值时一次也不该算。
后端因此不能把它摊成 C 的三元式（那会把两边都求值）——左边先落进一个临时量，
再写 `(tmp.tag ? tmp.payload : (右边))`。临时量只能落在函数里，所以顶层
初始化器走另一条路（那里两边都是编译期量，重复发一次没有代价）。

**`.?` 是"我知道它有值"，不是可恢复错误。** 没有 `try`/`catch`、没有异常传播：
空值解包是程序 bug，处置方式与整数除零完全一致（§7.R10）——`fflush(stdout)` →
stderr 一行 `zx: unwrap of a null optional at 文件:行` → `abort()`。要可恢复就用
`if` 捕获（§8.1）或 `orelse`，三条路各管一段，不需要第四种。

**都不是左值。** `x.? = 1` 报"cannot assign through a read-only path"。
载荷的地址本来就能拿（`&x` 等于 `&x.payload`，§5），真想改就 `*&x = 1` 或者
干脆别用 `.?`——给解包加写权限会把"读过一次标签"和"再写一次"之间的窗口
藏起来。

**编译期能定就定。** `const NONE: ?i32 = null; const F: i32 = NONE orelse 42;`
折成 `42`；`const N: i32 = SomeConst orelse 0;` 也折得出来。

> **v0.21 修正**：本节最初写成"`null orelse x` 恒为 `x`、`null.?` 编译期不折"，
> 这是错的——`null` 压根不是值（见 §59）。现在 `null.?` / `null orelse x` 都是
> 类型错误；编译期已知为空的可选值再 `.?` 也直接报错，不留到运行期。

## 58. switch 捕获：被捕获的就是"匹配到的东西"（M28）

M27 留下的尾巴：`switch (s.tag)` 之后还得手取 `s.circle`——模式说了是什么
变体，载荷却要再写一遍。v0.20 把捕获补上：`switch (s) { .circle: r { … } }`，
`r` 直接是载荷。

**一条规则覆盖所有主语**：被捕获的就是"匹配到的东西"。联合体臂捕获变体载荷
（各臂类型可以不同）；`?T` 的 `.some` 捕获载荷（`.none` 没有载荷，捕获直接报
错）；`!T` 的 `.ok` 捕获载荷、`.err` 捕获错误值（和 `if` 失败捕获同一套类型）；
枚举 / 整数 / bool 的臂捕获主语值本身。捕获是只读绑定，作用域限臂。

**语法判据只有一条：名字后面紧跟 `{` 还是 `:`。** `switch (s) { .circle: r { … } }`
是捕获（名字后面是 `{`），`.circle: a: { …; a: v; }` 是臂标签（名字后面是 `:`，
给收割用；v0.22 起标签挪到冒号后面，见 §60）。两者形状
接近但角色不同：标签是把臂的值交出去，捕获是把主语的值拿进来。捕获只配块臂——
`cap 值` 和裸表达式臂（`.red: v`）在语法上无法区分，索性不允许；单值臂本来
就省花括号，捕获场景几乎都带逻辑。多模式臂（`.a, .b: v {}`）拒绝：模式不同
载荷类型就不同，`v` 的类型无法唯一。

**实现上最省的形态**：解析器只多记一个名字（名字后跟 `{` 才收）；sema 在
`check_switch` 里给臂开一层作用域、塞一个 `SK_CAPTURE` 符号——和 `if` 捕获
同一机制；后端在臂体前发一行捕获声明。主语是聚合（`?T` / `!T` / 带标签
联合体）或有捕获臂时，先把主语落进临时量 `_swN`，头部用 `_swN.tag`，
载荷用 `_swN.u.成员` / `_swN.payload`——**这一步顺带修掉一个潜伏 bug**：
sema 的穷尽性检查早就支持 `?T` / `!T` / 联合体主语，但后端会直接发
`switch (struct)`——非法 C，没有测试覆盖所以从未暴露。

**没做的**：值位置 + 捕获（`let x = switch (o) { .some: v v*2, … }`）——
要它就得给 switch 的值机制动手术（块臂现在靠收割交值），等真需要再说。
类型模式（`i32: …` 按类型分派）也一样：和变体模式的歧义消解值得单独设计。

## 59. `null` 只填空，不当值（v0.21）

一句话：`null` 不是"空的可选值"，是**给 `?T` 填空用的那个字面量**。它没有自己的
类型，只在有期望类型的位置成立——初始化、赋值、实参、返回、字段。离开这些位置
就是编译错误：

```zx
let a: ?i32 = null;        // 对：落点是 ?i32
f(null);                   // 对：形参是 ?*T
let b = null;              // 错：没有落点，推不出类型
null.?;                    // 错：没有 payload 可解
null orelse 42;            // 错：没有"左边是不是空的"可问
```

后两条 v0.19 时曾被实现成"能跑"：`null orelse x` 直接发右边，`null.?` 留到运行期
abort。那是把**写错**当成**能跑**，和 §54 那两个静默错误是同一类病。v0.21 一律在
类型检查处拦掉，四条一起看规则才立得住。

**为什么不做"`null orelse x` 恒等于 x"这种便利**：一个恒等式只在一种写法下成立，
就一定有人用它，`null` 又被当成值用，规则重新变模糊。宁可让写的人多写一行
`const NONE: ?i32 = null;`——那行声明本身就是文档，还顺手给了它一个名字。

**顺带补齐对称**：编译期就能看出为空的可选值再 `.?`，也报编译错误（E0506），
和编译期除零（E0505）同一处置。R10 既然说"能定就编译期定"，那"必然 abort"
就不该留到运行期：

```zx
const Z: ?i32 = null;
const V: i32 = Z.?;        // E0506：编译期就空了

var z: ?i32 = null;
z.?;                       // 照旧：运行期才 trap（z 可以被赋值）
```

## 60. 标签是块的名字：写在条件 / 模式之后（M29）

> **v0.24 修订**：循环的标签改到关键字**前面**（`done: while (…)`）。
> 块仍然是"标签紧贴块"。理由与最终规则见 §63——本条的历史推演保留原样。

标签原来只有前缀写法（`tag: if (…) { … }`、`tag: for (…) x { … }`）。块臂里
另有一个"臂标签"，位置在模式与冒号**之间**（`.circle a: { … }`）——两套位置，
读的时候得先记住"这个 `:` 是分隔符还是块名"，写的时候也容易放错。

v0.22 把它收成一条：**块臂头部的名字，后跟 `{` 是捕获、后跟 `:` 是标签**，
两者可同时出现（捕获在前）。这条规则在四个地方完全一样：

```zx
switch (s) {
    .circle: r a: { a: r * 2.0; },   // 捕获 r，块名 a
}

if (o) v t: { t: v; } else { t: 0; }

const w = while (true) done: {
    if (n == 7) { done: n * 10; }
};

const i = for (0..8) k hit: {
    if (k == 3) { hit: (i32)k; }
} else -1;
```

**为什么 while / for 的标签挂在循环上，而 if 的挂在块上**：`done: v;` 要能结束
循环——如果标签只贴在循环体块上，收割跳到块末，下一轮条件再判，死循环依旧。
if 没有这个问题（块末就是分支末，if 随即结束），挂块上语义等价，读起来还更
贴近"这是这一臂的值"。

**switch 臂标签换了位置**（破坏性）：`.circle a: { … }` 现在报一条指路的错误
（"the arm label goes after the `:`"）。旧位置与新规则只差一个位置，静默接受
两种写法会让"标签到底属于谁"重新变模糊。

**顺带定下"没有 else 的 if 也能当值"**：`const i = if (true) tag: { tag: 5; };`
——类型由 then 臂给出；条件为假时没有臂执行，值就是零值，和"块没被收割就是
`{}`"是同一条规则。条件是编译期已知为假时，类型被剪成 `void`，那就没有值可
绑定：后端不再发 `void j = {0};`（非法 C），而是只发初始化器的语句部分——
绑定"没有值"的名字可以，引用它的地方照样没有类型。

**实现**：解析器在 `parse_if_arm` / `parse_while` / `parse_for` / `parse_switch`
各加几行（同一个"`{` 还是 `:`"判据）；sema 的 `check_if` 在无 else 时用 then
臂的类型；后端只改了 `gen_decl_inner` 的 void 分支——标签作用域本来就由
`NK_IF` / 循环 / 块自己的 `label` 承担，一个字没动。

**没做的**：`for` 无绑定 + 标签（`for (xs) lbl: { … }`）——普通 `for` 的绑定
不是可选的，先要求写 `for (xs) x lbl: { … }`；inline for 不参与标签（没有
运行时循环可跳出）。

## 61. 错误处理的四种出口：`try` 是明式的，不是异常（v0.23）

检查"处理错误的方式完不完善"时，先量了一遍代价。三层调用链原来要这样写：

```zx
const read_head = fn (p: []const u8) !i32 {
    let r = open_file(p);
    if (r) fd {
        if (fd < 0) { return (error)Err.read; }
        return fd + 1;
    } else e {
        return e;                    // 把捕获到的错误码重新包回去
    }
};
```

七行，中间还夹一层 if。四层就是四个套娃。**错误处理的主体是传播**，而传播
在最常见的形态上（"我在中间层，出错交给上面"）写得比 Go 还啰嗦——Go 至少是
`if err != nil { return err }` 一行。

### 为什么加 `try`

`try e` 完全等价于 `if (e) v { v } else err { return err; }`，一行写完：

```zx
const read_head = fn (p: []const u8) !i32 {
    let fd = try open_file(p);
    if (fd < 0) { return (error)Err.read; }
    return fd + 1;
};
```

规格 §5.1 早先写着"不做 `try`/`catch` 那套"。那句话反对的是**异常**——隐式跳转、
栈展开、看不见的退出点。`try` 不是那类东西：

- 调用点写着 `try`，读者一眼看到"这里可能退出"，和 `return` 一样显式；
- 没有栈展开，没有 catch 块，没有新的控制流构造；
- 返回类型不变，还是那个 `!T`，错误值始终在返回值里。

所以它不是"引入了异常"，是把 `if (…) return e` 这个已有的明式写法**压成两个词**。
（Zig 的 `try` 同一语义；Rust 的 `?` 也一样，只是写成后缀。选前缀是因为 Zx 的
`?` 已经被 `.?` 占了，`e?` 和 `.?` 摆在一起会分不清。）

### 四种出口的分工

| 写法 | 用在 | 出错时 |
|---|---|---|
| `try e` | 我在中间层，说了不算 | 带着同一个码 `return` |
| `if (u) v {}` | 就地处理这一处 | `else e` 拿到错误码 |
| `a orelse b` | 有合理的默认值 | 取 `b` |
| `a.?` | 这里不该出错 | 打一行说明后 `abort()` |

四条不是"功能重叠"，是**四种不同的意图**。混着用，读代码的人就分不清作者是
想过出错、还是在赌它不出错。

### 三条边界

- **`?T` 不能 `try`**：空不是错误，没有错误码可往上带。这种"没有"要么给默认值
  （`orelse`），要么就地分支（`if` 捕获）。
- **函数必须能返回错误**（`!U`）。错误得有个地方去，否则编译期就报。
- **`defer` 体里不能 `try`**：defer 在返回路径上执行，它自己再"提前返回"会把
  正在返回的值覆盖掉。就地处理掉。

### 顺带修掉的四个真 bug

这一轮真正花时间的不是加 `try`，是把错误联合体周边那些"编译过、答案错"补上：

1. **`!void` 三条成功路径全被堵死**。`fn f() !void { }` 报"能走到函数末尾却没
   返回值"、`return;` 报"这个 return 没有值"、`return {};` 报"expected `!void`,
   found `{}`"。也就是说**这种函数根本无法正常返回**——而它是最常见的错误签名
   （"可能失败的副作用"）。根子在 `check_return_paths` 只给 `TY_VOID` 开了口子，
   以及后端把 `!void` 当普通 `!T` 发（生成 `typedef struct { void payload; … }`，
   C 不允许）。
2. **错误码 0 静默吞错**。`error ≡ u16`，0 表示"无错误"，而枚举首成员默认是 0：
   `const Err = enum { open, read }; return (error)Err.open;` 发出去是 tag 0，
   于是"出错了"变成"成功了 + 一段未初始化的 payload"，调用方拿着垃圾继续跑。
   现在 `(error)X` 里 X 编译期能算出 0 的一律报 **E0508**（字面量和枚举变体都查），
   命名错误码从 1 起。**规格自带的 `spec/examples/errors.zx` 就踩了这个坑**。
3. **`!void` 的载荷被当值捕获**。`if (x) v { … }` 对 `!void` 生成
   `void v = _c0.payload;`，C 直接编不过。现在语义层直接说清楚："这个联合体没有
   载荷可捕获，成功分支写 `if (x) { … }`"。switch 的 `.ok` 臂同理。
4. **`main() !void` 生成非法 C**（收尾时才发现）。`main` 的 C 签名是 `int main(...)`，
   后端对返回语句无条件加了个 `(int)` 强转：`return (int)((ZxErr_void){ .tag = 7 });`
   ——结构体转 int，C 直接拒绝。后果是**最想用的那种签名根本编不出来**，而
   `try` 在 `main` 里的提前返回走的是另一条路（先造一个联合体临时量再 return），
   同样非法。
   `main` 的返回值本来就要折一次：`!T` 用**标签本身**当退出码（0 = 成功，正好是
   shell 的约定），`?T` 有值 0、空 1。折完之后 `try` 一路传到进程边界就完整了——
   否则"四种出口"缺了最后收下的那个人。

   **顺带发现测试根本没在跑**：runner 用 `contains(src, "fn main(")` 判断"这个
   文件有入口，值得编出来跑一遍"。v0.24 把入口改成 `const main = fn (…)` 之后，
   这个判断对全部 48 个文件都不成立，于是 47 个 `// expect-output` 用例**静默
   退化成纯类型检查**——套件照样报绿，运行期行为无人验证。现在两种写法都认，
   并加了 `// expect-exit:` 断言退出码（错误处理的收尾就是退出码，不钉住等于
   没测）。修完后用例数从 135 涨到 183，多出来的 48 条全是真正跑起来的。

### 还留着的两件事（都不打算现在做）

- **`?!T` / `!?T` 不合法**（§5）。"既可能错又可能没有"要么把"没有"也做成错误码，
  要么用带标签联合体。这是有意的：三个维度的状态混在一个值里，调用点就读不出
  该判哪一个。
- **错误码是裸 `u16`，没有命名空间**。两个模块各自定义 `Err`、都用 1，上层拿到
  码 1 分不清是谁。当前靠约定（同一处定义 / 分号段）。要做就得引入 error set 类型，
  那是另一轮的事。

## 62. 内建字段与同名字段：字段优先（v0.23）

`.len` / `.size` / `.ptr` 是**编译器字段**，不是内存里的成员。规格 §3.3 原来写着
"这三个名字不能再作为结构体字段名，声明时报错"——但 `std.BufWriter` 自己就有
`len: usize`，而且那是合理的（"已缓冲的字节数"）。

真正的错不在"允许不允许"，而在**三处判断不一致**：

| 位置 | 旧行为 |
|---|---|
| `check_field`（类型检查） | 结构体走普通字段查找 → `h.size` 是 `i32` |
| `ct_field`（常量折叠） | 无条件当字节数 → 折成常量 8 |
| `ex()`（代码生成） | 无条件当字节数 → 发 `layout_size(h)` |

于是 `struct { fd: i32, size: i32 }` 的 `h.size` 静默变成 `sizeof(h)`：
**编译过、答案是 8**。这类错比编不过严重得多——它是这一轮唯一一个靠"给自己的
测试用例起个正常字段名"才撞出来的 bug。

规则统一成一句：**聚合体自己有同名字段时，字段优先**。要类型大小写 `@sizeOf(T)`。
三处一起改（`check_field` / `ct_field` / `ex` + `is_const_init`），规格 §3.3 同步。

不选"禁止这三个名字"的理由：它把一个**三处不一致的实现 bug** 变成**一条语言限制**，
而限制本身没有收益——字段优先是唯一没有歧义的读法，`@sizeOf` 也已经在了。

## 63. 标签写在被离开的结构前面；函数定义只剩 const 一种（M31）

### 标签

M29 把标签定成"块的名字"，套到循环上就矛盾：`while (true) done: { … }` 里
`done:` 贴在**体**前，读起来是体的名字；可 `done: v;` 要离开的是**循环**——
只跳到体末的话下一轮又进来了。实现可以把它挂在循环节点上（M29 就是这么做的，
语义正确），但读代码的人看不出这一点，只能靠记。

两条路：

1. 保留后缀，靠"循环的标签语义特殊"来解释。每次看到 `名字 :` 都要先想
   "后面跟的是块还是循环"。
2. 循环的标签挪到关键字前。块的标签仍紧贴块。

选了 2。判据只剩一句：**标签写在被它离开的结构前面**。块 → `t: { … }`；
循环 → `done: while (…)`。于是"标签在体前"这个位置根本不存在，
`while (…) tag: { … }` 报错并给出正确写法。不静默兼容两种位置——都收的话，
规则等于没有，而这一整轮的收益就是把规则说成一句。

`if` 两种位置都成立（`t: if (c) { … }` 与 `if (c) t: { … }`）：它的标签贴的
就是块，两种写法指同一个作用域。不为此删掉前缀——`const sign = s: if (…)`
读起来是"这一整个 if 叫 s"，也很常用。`continue :tag;` 不受影响，它本来就
只写标签名、不关心位置。

### 函数定义

`fn name(…) R { … }` 与 `const name = fn (…) R { … };` 语义完全一样（自递归、
取地址、传参、导出都没差别），差别只在 AST 形状：前者是带 name 的 NK_FN，
后者是 NK_DECL 包 NK_FN。两套写法没有收益：

- "函数名"和"绑定名"合成一个概念之后，`fn` 后面永远直接是参数表，解析器少一个
  分支，读者少一次判断；
- 报错要用的函数名从 `fn->name` 换成 `fn->sym->name`，只有一处；
- 方法也一样（`const add = fn (self: Self, …)`），体里不再有两种成员形状。

保留 `extern fn name(…) R;`：它没有函数体，指向别人已经编好的符号，名字的意义
在编译器外面，`fn` 后面那个名字是 C 符号本身。

代价是仓库内 339 处定义要改写，一次性机械替换即可。早收窄比晚收窄便宜——
以后每个新读代码的人都不用问"为什么两种都行"。

### 顺带修的 bug

`ct_call`（编译期折叠调用）在**调用方**模块里重新检查函数体：跨模块调用时，
被调函数引用的私有辅助函数全变成 unknown identifier。`instantiate` 早就切了
模块上下文，`ct_call` 漏了同一手。修法照抄——按 `callee->fn->sym->mod` 切
`g_mod` / `g_scope` / `g_srcpath`，每条 return 路径都恢复。

## 64. runner 换成 C：测试工具不能丢报告（M32）

旧 runner 是 Zx 写的（§53），它证明过语言能写长命程序，但它有两个位置不对的问题：

1. **报告会丢。** 它用 `system()` 拼 cmd 行起子进程，stdout 被重定向时是整块缓冲，
   实测 1/6 概率整份报告消失。测试工具把自己伪装成"通过"，比测试失败严重得多。
2. **它不计量。** 编译慢了一倍，它照样说"全过"。

换成 `tools/runner.c`：自己 `CreateProcessA`（POSIX 走 `fork`+`execv`），
重定向 / 超时 / 计时全自己管，不经过 shell。判定规则一条没改（协议是资产）。

### 量出来的两件事

**a. 全局名字查找是 O(N²)。** 规模曲线第一次跑出来：8000 个顶层函数 437 ms，
16000 个 1.82 s——每翻一倍耗时 4.3 倍。根因是作用域用链表存符号、`lookup()`
每个名字从头走。给每个作用域加一张哈希索引（链表仍是权威：顺序、遍历、快照都
看它；表只回答"这个名字在不在"）之后，8000 个降到 99 ms，16000 个降到 176 ms。

值得记的是**为什么以前没发现**：136 个测试文件里最大的 200 行，链表还是哈希表
都一个样。性能问题不在单点用例里，在规模里——这就是把"规模曲线"做成常驻检查
而不是一次性 benchmark 的原因。

**b. 一个一直在的 UB。** 加索引让 `Scope` 从 24 字节涨到 48 字节，
`tests/good/generic-alias.zx` 立刻段错误。`-O0 -g`（zig 运行时检查开着）报得很
干脆：`snap_scope` 读到的 `is_module` 是 112。栈上的 `Scope` 从来没清过这个字段，
多数时候栈上残留恰好是 0；一旦不是 0，就把栈上作用域当成模块作用域存进待检查
队列，栈帧一没就是悬空指针。

修法是 `scope_push` 把四个字段一起清。更重要的是加了个开关：

```sh
ZX_CHECKED=1 sh test.sh     # 用 -O0（运行时检查开着）的编译器跑同一套用例
```

它把"运气好才不发作"变成"确定性失败"。这类问题靠加测试用例是防不住的，
得换编译档位。

### 基线只比规模曲线

试过按单项耗时做基线，测不下去：进程启动的抖动 ±5 ms，比一个测试文件的前端耗时
还大，同一份代码连跑两次能"快 22%"。最后只比规模曲线——单进程、净耗时 80 ms 起，
抖动 10% 以内，阈值定在 25%。**阈值必须画在噪声之外**，否则红灯会变成背景噪音，
人就开始忽略它。

### 没做的

- **不并行跑用例。** 计时一旦并行就不成立，而计时是这个 runner 存在的一半理由。
  真要提速，应该并行在"编译器自己编译多个模块"那一层。
- **不把 C 版本的能力倒推回 Zx 版本。** 两个 runner 同时维护等于两份协议，
  `runner.zx` 留在仓库只作自举迁移试验的目标（`spec/bootstrap.md`）。

## 65. char 字面量做 switch 模式（v0.25，G2）

自举评估里最后一个语言缺口。`selfhost.zx` 的词法器按字节分派，以前只能写
`switch ((i32)c) { 48, 49, 50: … }`——数字读不出是哪个字符，还得显式转换。
`'a'`、`'\n'`、`'中'` 现在都是模式，和整数字面量同一套规则。

### 定型：按落点，不另立类型

char 字面量在表达式位置是 `u8`（它是字节）。放进模式里如果也锁死 `u8`，
`switch (cp) { '中': … }` 对 i32 的码位 subject 就比不上。规则照抄整数字面量
的拟合检查：**模式里的 char 按落点定型**——subject 是 `i32` 就按 i32 的码位
比（`'a'` 即 97），没有落点（`u8` subject）才是 `u8`。码位超出落点范围报
"char literal does not fit"，与 `let c: u8 = '中';` 是同一条检查——静默截断
成 0x2D 正是 R10 要禁止的那类错误。

### 逗号判据：能不能开一个新模式

修 char 模式时撞出旧规则的洞：多模式列表里"逗号后面只认整数和 `.成员`"，
`'a', 'b':` 被拆成两条臂（第二条缺冒号报错），`true, false:` 和 `-1, -2:`
同样被挡。判据换成一条 `starts_pattern`：下一个 token 能开一个新模式
（`.成员` / 整数 / char / `true` / `false` / 负号 / `(`）才续列表。
`1: …, 2: …` 的逗号后面是整数模式开头——但下一轮循环本来就要开新臂，
两种情况由同一个判定自然分流，不需要特例。

### 不做的

- **字符区间**（`'a'...'z'`）没加。区间模式要新 AST 节点、sema 和后端各一条
  路径，而整型区间尚未立项；等整数区间做时一起设计，避免两套形状。
- **`u8` 之外的 char 类型**（UTF-8 码点类型、`u21`）没立项。现在的 char
  字面量就是"能装进落点的码位"，多字节字符靠码位当整数用，够到自举为止。

## 66. 容器的性能来自内存原语，不来自更聪明的循环（v0.25）

### ArrayList：逐元素循环是瓶颈的根源

`reserve` 搬家、`insertAt` / `removeAt` 挪动、`append` 批量追加，原先都是
`(buf + i).0 = (buf + j).0` 这样的逐元素循环。T 是泛型参数，每次循环体是
"按元素大小访存一次 + 判断一次"；对 8 字节元素 C 编译器也许能向量化，
对 24 字节的切片就未必——性能靠运气。改成 `@memcpy` / `@memmove` 之后：
一次调用、SIMD 路径、与元素大小无关。语义不变：搬移用 memmove（同
buffer 内必然重叠），追加用 memcpy，边界上的零长度调用显式跳过。

没有为 `resize` 的 fill 换 memset：填充值是任意 T 的值，不是字节模式，
那个循环本来也不在热点上。

### HashMap：缓存哈希，探测不碰字符串

每槽加一个 `u64` 哈希（0 = 空槽，FNV 结果为 0 时压成 1），三处收益：

1. **探测先比哈希。** 热点路径上哈希不同就不用碰键切片（16 字节）和
   str.eq（逐字节）——8 字节的哈希数组更贴缓存。
2. **扩容不重算、不比较。** 键在旧表里本来就唯一，新表里找第一个空槽
   放进去就是正确的线性探测结果；旧实现每个键重算一次 fnv1a、探测时
   还要对每个撞位键做一次 str.eq。
3. **clear 是一次 memset。** 顺带把 keys 数组从 `?[]const u8`（24 字节
   带标签）换成 `[]const u8`（16 字节）+ 哈希判空——每槽省 8 字节，
   空不空只看哈希。

`putNew` 从"get 一次 + put 一次"改成一次探测同时完成查旧和插入：
原先哈希两遍、探测两遍。

### 校验和先行

改动前先给容器建了 bench（bench/containers.zx）：五个负载各打一个
FNV 校验和，优化前后必须逐位一致——ArrayList 和 HashMap 的实现是全换，
只有校验和能证明语义没漂。交替实测（新旧二进制轮流跑 6 轮取中位）：
整体 171 → 131 ms（约 -23%）。单项噪声 ±20 ms（这台机器上还有别人在
干活），所以结论只从"交替对比"里出，不盯单条。

### 代价

语言多了三个内建（解析 3 行、sema 一个分支、后端一个分支、生成 C 多
include 一个 string.h）。换来的是：以后所有容器代码都有正当的批量搬运
出口，不用再靠"碰巧被编译器向量化"。

## 67. 自举阶段 2：对拍的是 AST 字节，不是"感觉差不多"（M35）

Zx 版语法分析器（bootstrap/parse.zx，约 1200 行）要证明与 src/parse.c
等价，靠的是**逐字节 diff AST 序列化**，不是肉眼看结构像。这逼出两条前置：

### 先定死序列化格式，再写第二份实现

对拍的先决条件是 C 侧 dump 格式本身无歧义。落地时发现浮点节点用
`%g` 输出——`1.50` 会打成 `1.5`，Zx 侧就得再实现一遍 %g 的舍入规则，
纯属对拍噪声。改成直接打印原始 token 文本（词法器早就保留了）：
**序列化应该携带源信息，不该携带格式化决策**。

### 共享出参在递归下降里会被嵌套污染

C 版把 `if` 捕获名用**栈上指针出参**传给调用方——每层 parse_if 各有
各的局部变量，天然隔离。Zx 没有"指向局部变量的指针"这个习惯用法，
改成了 Parser 上的共享字段 `self.cap`：臂在开头写入，调用方在臂
parse 完后读回。

这有个时序洞：臂的块里若有嵌套 `if`，内层 parse_if 入口会
`self.cap = null`，而外层要等**整个臂（含全部嵌套）parse 完**才读回——
捕获名丢了。修法是模拟 C 的栈语义：parse_if 入口保存、读回后恢复，
else 臂读回后同样恢复。教训记一句：**把 C 的按引用出参改写成共享
可变状态时，凡"写入点深、读取点浅"的都要配保存/恢复**。

### 两边都拒收的输入也是对拍样本

spec 里的反例片段两个解析器都该拒收，但"都报错"不等于"报同样的错"——
对拍脚本只要求两边 rc 一致即跳过，错误消息的对齐留给诊断阶段
（自举阶段 3 之后）。对拍的分阶段目标：先 AST 全等，再诊断全等。

## 附：明确不做的事

- 无 GC、无析构、无 RAII、无生命周期标注、无借用检查
- 无 trait / interface / 类型类、无重载、无默认参数、无变参
- 无异常（只有 `!T`）、无协程 / async
- 无隐式数值转换（只有 R7 那 5 条免拷贝提升）
- 无宏系统（编译期函数就是宏的替代品）
- 无运算符重载
- 无 `private`（可见性只有 `pub` 一个开关，见 §18）
- **无 cast 类内建**（v0.26）：`@ptrCast` / `@bitCast` / `@intCast`
  不存在——类型转换只有 `(T) v` 一种写法

## 68. 空值当错误：`error.null` 是错误集合的保留成员（v0.26）

**裁定一：cast 类内建不存在。** 规格里挂过名的 `@ptrCast` / `@bitCast` /
`@intCast`（§14 表）编译器从未实现过——正好趁对账清掉。保留它们的唯一
后果是"三个 cast 该用哪个"的选择题：指针互转 `(T)p`、位重解释走指针
`(*i32)(&f).0`、窄化 `(u32)n`，都是 C 风格转换的既有职责。写法唯一，
行为查同一张表（§7.R4）。

**裁定二：`?!T` / `!?T` / `??T` 全部不合法**（E0305，编译器早就在拦），
规格 §5 原来那段自相矛盾的话（"`?!T` 是编译错误……把 `?T` 当载荷
（`!?T` 仍不合法）"）重写掉。嵌套表达不了"可能没有 + 可能出错"。

**裁定三：空值当错误。** 那这两个需求叠加时写什么？答案不是嵌套，
是给错误集合一个保留成员：

```
error.null ≡ 65535        // u16 最大值；命名错误码不许占用（E0508）
```

- `try` 的左值从此接受 `?T`：有值取载荷，空抛 `error.null`。原来那句
  "`?T` 的空不是错误，没有错误码可往上带"作废——现在有码了，就是 65535。
- **`if (o) v { … } else e { … }` 对 `?T` 非法**：值臂 `v` 是"?"、
  错误捕获臂 `e` 是"!"，同框就是被禁的 `?!T`。else **捕获**只属于
  `!T`（`!void` 想要错误码写 `else e` 照旧）；`?T` 的空要么
  `else { … }` 不带名，要么交给 `try`。这条是用户裁定的直接推论——
  编译器原本给 `?T` 的 else 捕获一个 bool 标签，那是把 `?!T` 从
  类型层赶出去又从语法层放回来。
- 传播路不变：`null` 沿 `try` 上行到 `main` 变退出码（Windows 原样
  65535，POSIX 截 8 位得 255）。

**为什么是 65535**：0 已保留给"无错误"，命名码从 1 起且实际都太小；
u16 最大值在顶部，碰撞概率为零，查找方便。代价是 `(error)65535` 被禁
（E0508 扩到两个保留值）——可接受，用户没有理由手造一个"null"。

**不改变的部分**：`orelse` / `if` 捕获对 `?T` / `!T` 的行为照旧；`?T`
到 `!T` 没有隐式转换——"空值当错误"只在 `try` 和 else 捕获这两个
**显式错误上下文**里发生。要就地分辨"没有"和"真错误"，本来就不该
`try`。

## 69. std.Pool：空闲链内联进负载；基准必须防"死分配消除"（M36）

**为什么不照搬 Zig 版**：ecs 的 `pool.zig` 把槽位管理整个建在
`Memory(Slot, false)`（世代槽位表）上——池的重复释放检测、O(1) 分配
都来自它。但 std 不能反向依赖 ECS，所以槽位管理换成了自包含的方案：
每个档位一条"整批槽区"链（槽位从不搬动，发出去的指针始终有效），
空闲链**内联**在被释放块的负载前 8 字节（最小档 16B，装得下），分配 /
释放都是栈顶操作。重复释放检测不靠世代表，靠块头 flags：LIVE→FREED
置位时检查，FREED 的块再 free 直接拒绝且不写任何东西——空闲链因此
踩不坏。

**世代号保留**：块头里的 `gen` 每次 free 加一，主要给调试器 / 后续
句柄化用；`free` 的判定只看 flags。

**classCount=19 的坑**：线性段 16…128 步进 16 是 8 档不是 7 档。
写错的表现极坏——每次 `init` 都越界写堆，但崩溃延迟到进程退出
（堆损坏在 CRT 收尾才爆发），而且 stdout 全程缓冲、崩了就丢。
教训有两条：① 铺档循环的迭代次数之和必须正好等于档位常数，这条
关系值得写在常数旁边；② 崩溃丢输出时用**退出码**做逐步标记，别
指望 printf。

**`?*T` 排序环（backend.c）**：`ensure_type(?*Region)` 会递归进
`ensure_type(Region)`，而 `Region { next: ?*Region }` 的身体引用
Opt 的 typedef——此时它还没发射。修复：`?*T` / `[]T` 的载荷是
指针，C 里指针指向不完整类型合法，所以只需要前向声明——加
`ensure_fwd`（state=3 表示"名字已落、身体待补"，`ensure_type`
见到 3 就继续补身体），`?*T` 先落名字再发 typedef 最后补身体；
`[]T` 同理。`?T`（载荷按值）不走这条路——按值要求完整类型，
而按值自引用在类型系统里本来就不可能成环。

**基准防 DME**：malloc/free 成对出现时 clang 会整个删掉（死分配
消除），对照组会测出 1 ns/对这种假数。必须维持一批活块（环形
1024，释放 1024 步前的旧块）才能逼真地走 allocator。实测
（ReleaseFast、10M 步、轮转 4 档）：池 ≈11 ns/对，裸 malloc
≈27 ns/对。池赢在：档位内是纯指针栈操作 + 块头一读一写，没有
malloc 的尺寸分桶查找和元数据维护。

## 70. 自举阶段 3：切换的边界画在"AST 序列化"，鸡蛋问题用 --fe=c 过河（M37）

**切换点**：`zxc` 默认不再用 C 解析器——`src/fe.c` 起子进程跑
`bootstrap/zxfe.zx`（约 250 行的 Zx 前端驱动），zxfe 把源文件解析成
**可装载的序列化 AST**，`src/astload.c` 在 C 侧重建 Node 树交给
sema/backend。诊断由 zxfe 按 `path:line:col: error[CODE]: text` 同一
格式直接打到 stderr，zxc 只看退出码——错误通道不串两套措辞。

**序列化格式定死的三条纪律**：

1. **枚举转编号，不转名字**。kind/op 写成与 `ast.h` NodeKind /
   `zxc.h` TokKind **同序的整数**，装载器按编号重建。文本名字看着
   友好，但要维护一张双端对照表——编号天然同步，前提是两侧枚举
   不许乱序（这是阶段 2 对拍逼出来的约束，白捡）。
2. **浮点传位型，不传十进制**。fval 按 64 位位型写（Zx 侧对
   `&n.fval` 做指针重解释取位型），装载器 memcpy 回来——走十进制
   会在 `%.17g` 这类边界丢精度，位型永远逐位相等。
3. **字段映射的分歧按 kind 特判**。DECL 的种类 Zx 记在 op2、C 在 op
   （历史形状差异）；`union(enum)` 糖标记同理。装载器不是通用反序列化，
   是"知道两侧形状"的胶水——假装它通用只会把分歧藏得更深。

**鸡蛋问题**：zxc 默认连**模块加载**都走 Zx 前端，所以编 zxfe 本身
也要过前端——而此刻手上的 zxfe 还是上一版。实测直接炸：新 char 语义
（字面量要算出码点）旧 zxfe 没吃进去，char 模式的值全变 0，编译
`duplicate case value '0'`。结论：**自举第一步必须踩着 C 前端过河**——
build.sh / test.sh 编 zxfe 一律加 `--fe=c`，等 zxc 能用新 zxfe 自举
出新 zxfe（阶段 4）这脚才能拆。

**char 补值是阶段 1"够用"边界的账单**：`lex.zx` 当时刻意没算 char
字面量的值（对拍只比词法单元文本，够用）。切到 Zx 前端当生产路径后
立即暴露——补 `char_cp`（UTF-8 解码 1..4 字节成码点）+ `emit_char`。
教训：对拍边界上"刻意不做"的事，要记着它是债，切换日就是还债日。

**Windows `system()` 引号陷阱**（第二次踩）：命令行**不能以引号开头**，
`cmd /c` 会把首尾一对引号整个吃掉，报"文件名、目录名或卷标语法不正确"。
与 main.c 拼 zig cc 命令行时同一约束——让 `dir\zxfe.exe` 顶在第一个
字符，参数里的路径才轮得到引号保护。

## 71. 自举阶段 4：位置也逐字节相等；默认开关一翻，验证工具的含义就变（M38）

**位置进对拍**。阶段 2/3 的 AST 对拍只比结构，节点 line/col 是
"cur() 近似、留给阶段 4"的悬账。阶段 4 把 ` @L:C` 加进 dump 头
（C 侧 ast_dump 与 Zx 侧 dump 同位插入），对拍升级为"结构 + 位置"。

**教训：默认开关一翻，老命令的含义就变。** `zxc --ast` 在阶段 3 之前
= C 前端的 dump；阶段 3 之后 = Zx 前端的 dump。不改脚本直接跑
diff_ast.sh，比的就成了 Zx 对 Zx——同一个解析器 dump 两遍，当然全等。
第一轮位置实验就是这么被"61/61 全等"骗过的。验证工具必须跟着默认值
走：diff_ast.sh 现在显式 `--fe=c`。凡是依赖"某开关默认值"的验证脚本，
开关语义变化时都要重审一遍。

**C 的位置语义没有统一规则，是逐调用点的历史事实**，对齐就得逐点抄：

| 构造 | 位置来源 |
|---|---|
| 普通节点 | 引导 token（先存 t 再消费） |
| bin / un / orelse / 赋值 | 左操作数 |
| 类型点路径 field | **基标识符**（不是点） |
| struct / union 体字段 | **kw_struct / kw_union 自己**（整组共用） |
| enum 成员、解构 pattern 的 id | 成员名 / 绑定名 |
| for 绑定 | 名字**后**一个 token（先 take_ident 再 cur） |
| if 臂语句包装块 | **臂值节点**的位置 |
| else 捕获 id | if 关键字 |
| 解构 pattern 元组 | decl 关键字 |
| root | 钉死 (1,1) |

容易抄反的正是"没有规律"本身：for 绑定与解构 id 长得一样，一个取
名字后的 token、一个取名字本身——只看一行源码猜语义必错，得逐点看
调用顺序。Zx 侧加 `new_at(k, t)`（new() 保持 cur() 兜底），60/61
分歧文件逐轮收敛到 0。

**闭环与种子**。build.sh / test.sh 编 zxfe 不再带 `--fe=c`——zxc 用
自己的 Zx 前端编出**新 zxfe**（实测 `--ast` 输出与现役版逐字节一致）。
但全新 checkout 没有 `bin/zxfe.exe`，zxc 连入口文件都没法解析——
保留 `--fe=c` 作种子回退：第一次构建踩 C 前端过河，此后每次构建都是
Zx 编 Zx。这是自举的标准形态：**闭环是稳态，种子是冷启动**。

## 72. 阶段 A 两处前端 O(n²)：折叠负缓存与 cast 配对预检（M40）

自举收官后开"语言收口"阶段，第一件事是把 M32 只修了一半的规模问题修完。
M32 修的是 **sema 名字查找**（作用域哈希）；这次用同一套"规模曲线"方法
（合成 N 档源码、净耗时对比翻倍比）又量出两处，都在**表达式深度**这个
维度上——M32 的用例（N 个小函数）探不到它，只有深表达式才现形：

**a. sema 编译期折叠：`fold_expr` 每节点重走整条左脊柱。**
`check_expr` 每个节点都调一次 `fold_expr`，而 `ct_eval` 只缓存**折得出
值**的节点（`n->ct`）；运行时子树折不出值、**没有缓存**，于是深度 d 的
链上每个祖先的折叠都把 d 层重走一遍——8000 项 `a+a+…` 净 552 ms
（4 倍长度 22 倍耗时），8000 条**独立**短表达式只要 8 ms。修法是
**负缓存**：`Node` 加一位 `ct_no`，`fold` 在干净上下文里（stuck / flow
已存起再清空）折不出值就记账，`ct_eval` 入口见到直接短路。实测 631 ms
→ **4 ms**（约 150 倍）。

负缓存的正确性边界值一条注释：**只在检查阶段（`g_ct_exec==0`）读写**。
编译期执行阶段（`ct_run` / `ct_call`）里 var 槽位是活的，同一棵子树
算得出值——把"折不动"记到那个阶段去，comptime 循环就全废了。标识符
两种阶段都不缓存（同一条既有规则：槽位随时会变）。

**b. parse cast 消歧：每个 `(` 都试探一遍 parse_type。**
`(T)e` vs `(e)` 的消歧是"先试探着当类型读，读到 `)` 再看后面能不能跟
cast"。嵌套括号下，第 k 层的试探要把剩余 n−k 个 token 全部走完——
8000 层 `((((x))))` parse 净 222 ms。修法：**进 parser 前一次 O(n) 的
括号配对预计算**（栈式扫描，两供建表），消歧处先做 O(1) 必要条件检查
——真 cast 的 `)` 一定是配对那个（类型里括号自平衡），且其后必须能跟
cast；不满足直接走表达式路径，试探只留给真 cast。实测 222 ms →
**3 ms**。C 侧（`src/parse.c`）与 Zx 侧（`bootstrap/parse.zx`）镜像同
修，AST 逐字节一致（对拍 61/61）。

**方法论沉淀**：这次用的是"规模曲线 + 形态二分 + 分趟探针"三件套——
先多档放大确认超线性（顶层声明、局部变量、错误数都线性，唯深链二次）；
再用形态二分把变量分开（长链 vs 多语句、`+` vs `&&` vs 负号 vs 括号）；
最后临时计时器把 sema 三个趟分开，锁定 `check_fn_body`。探针留在了
`tools/probe_parse.c`（只链 lex/parse/ty/val/sema，报告分趟耗时）——
下次量规模不用再搭一遍。

**顺带的教训**：`--ast` dump 的缩进按深度打空格，输出量本身随链长
O(n²)——这是**格式的性质**不是实现的性质，真实代码深度小，不改。
做蓝图时把 M32 的"前端二次"当成未修的账挂在了待办上——**账本要跟着
代码走**：M32 修掉的部分当时就该从清单上划掉，这次先复测才没白修一遍。
