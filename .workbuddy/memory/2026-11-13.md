## §133 第三增量：Handle 证明账本 + 按点擦除 + 双发射（用户「继续」）

- 把 Handle 接进**同一份** `g_rslots`：`create` 发 `is_handle` slot、
  `free` 消费、`deinit` 按 `owner_sym` 整批标 `RS_DEAD`、`get` 是访问点。
  新增 `ProvePoint[]` 记每个访问点 PROVEN/OPAQUE + 原因串。
- **opt-in 约定**：容器同时有 `get` 和私有 `getUnchecked` 才启用；
  `std/slot.zx` 的 `get` 检查后转调 companion，用户手调会被 E0404 挡住，
  中介不可绕过。不硬编码容器名、不加内建、不改指针表示。
- **按点擦除的落地形态**：`check_expr(NK_CALL)` 在 `check_call` 返回后
  把 PROVEN 点的 `n->a->name` 改成 `getUnchecked`，泛型容器方法走
  `inst_name(n->inst, name)` 自动换 C 名，**backend 一字未改**。
  为什么不用「注入 checked 参数 + if 剪枝」：zx 无跨调用常量传播/内联特化，
  函数体内分支折不动。这是与 §130 原表述的实现偏差，已写进文档。
- **tainted 是硬约束**：`sema_construct` 对整个 `NK_IF`（含条件）加
  `g_flow_depth`，所以不能一见 flow depth 就判 opaque（`handle-erase.zx`
  的 get 在 if 条件里）。改为「发行点/作废点在控制流里就标 tainted」，
  既保住直线点的证明率，又不会把分支里可能发生的 free 擦成 UAF。
- **失效后使用不报 E 码**：`free` 后 `get` 返回 null 是 side table 的
  fail-safe 查询，`slot-table.zx` 的 stale/closed 就在用；做成 error 会逼
  删用例变绿。只给 OPAQUE 原因。§130 第 4 步的新 E 码因此未做。
- 档位：`src/main.c` 加 `g_zx_release`，四处 `g_cflags = release ? ...`
  同步赋值；`ZX_HANDLE_CHECKS=1` 强制保留全检查。`explain region` 默认 dev。
- 实测：`handle-erase.zx` 1/1 PROVEN、release 全擦；`slot-table.zx`
  0/7 PROVEN（原因含 already freed / table closed / control flow）；
  两档实跑都是 `get 11 / free true / leak 0`。
- 守门：新增 `tests/good/handle-erase.zx` + `test.sh` §133 段（账本与
  生成 C 双检查、release 真编译真跑、强制保留开关）。定向回归
  **27 个用例 passed 47, failed 0**；按项目节奏未跑全量。
